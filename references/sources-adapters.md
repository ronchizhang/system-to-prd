# 用例库与代码仓库：不绑定任何一家

这份包的最佳实践样本，是在「能连知识库 + 能连代码托管」的环境里跑出来的：用例从知识库读，代码从托管仓读。
但你手上可能是 Notion、飞书、语雀、Confluence、TestRail、一个 Excel，代码在 GitHub / GitLab / 自建 Git，或者只在本机某个目录。

这份文档只解决一件事：**换源怎么接，缺源怎么标，绝不假装核过。**

---

## 一、六源 → 你手上的具体东西

| 源 | 首选 | 等价替代（都算「已核」） | 都没有时 |
|:--|:--|:--|:--|
| `ui` 浏览器渲染 | Chrome 调试端口（`launch_chrome.py`） | Playwright / Puppeteer / 手动截图后放进 `snapshot/` | 原型只能凭印象，`status` 必须写 `未核` + 原因 |
| `api` 后端接口 | 页面里直接调，抓响应 | OpenAPI / Swagger 文件、Postman 集合导出、curl 结果贴上 | `未核` |
| `fe` 前端代码 | 本地 `git clone` 后读 | GitHub / GitLab API、构建产物 + sourcemap、用户上传 zip | `未核` |
| `be` 后端代码 | 本地 `git clone`（`harvest.py be --local`） | 托管平台 API（`harvest.py be --repo`）、IDE 里打开后贴片段 | `未核` |
| `ima` 用例 | 任意可搜索的知识库连接器 | `.xmind` / `.md` / `.csv` / `.xlsx` 导出放进目录；TestRail / Zephyr / 飞书多维表导出 | 业务口述替代，`status` 写 `部分` |
| `biz` 业务确认 | 只能问人 | — | **不许缺**：没有人的裁定，P0 事实一律停在待确认 |

> 源的名字（`ui/api/fe/be/ima/biz`）是数据契约里的固定键，**不要改键名**，它跟历史文档和门禁是绑定的。
> 换的是「它从哪读」，不是「它叫什么」。

## 二、给 AI 的作业流程（照这个顺序做，别问「你用什么工具」这种空问题）

### 1 · 开工先问三句，问完再动手

> 1. 测试用例现在放在哪？（知识库链接 / 一个 xmind 或 Excel 文件 / 没有，只能你口述）
> 2. 代码在哪？（本地路径 / 托管平台仓库地址 / 都没有）
> 3. 测试环境能不能登录？（要三个账号还是两个端）

### 2 · 用例源的发现顺序

```
① 有知识库连接器 → 搜「<模块名>」「<系统名> 用例」，命中就逐条读
② 没有连接器 → 在用户给的工作目录里找 *.xmind / *.md / *.csv / *.xlsx
③ 还是没有 → 让用户从 TestRail / 飞书 / Confluence 导出成 md 或 csv，丢进目录
④ 最后一步 → 让用户口述，口述内容写进 sources[ima].detail = "业务口述，未经用例库核对"
```

xmind 是分支树，不是清单：按功能点归并、砍掉不可判定的、每条挂到它守的规则上。三步在 `narrative.md`。

### 3 · 代码源的发现顺序

```
① 本地有仓库 → harvest.py be --local <path>；前端用 harvest.py chunks --dir <构建目录>
② 托管平台有连接器 / CLI → harvest.py be --repo <org/repo> --path <文件路径>
③ 用户能导出 → 让他把相关文件（controller / service / 前端 chunk）打包发过来
④ 都没有 → 代码两源写「未核」，并在交付说明里写明「后端规则未经代码核对」
```

**只读相关的几个文件，不要整仓扫。** 一个模块通常落在一个 controller + 一个 service + 一处前端 chunk。

### 4 · 缺源的写法（这一条是硬要求）

```json
{"name": "用例库", "status": "不可达", "detail": "未提供用例库连接器，业务口述替代，未与用例原文核对"}
```

- `status` 只能取 `已核 / 部分 / 未核 / 不可达`
- **`detail` 不许留空，也不许写「无」**——写清楚「为什么没核到」，读的人才知道这条结论的强度
- 门禁会查：`已核` 的源必须有不小于 3 条的 detail；空 detail 直接 FAIL

### 5 · 降级红线

| 可用源数 | 能不能开工 | 交付上必须怎么标 |
|:--|:--|:--|
| ≥ 4 源 | 可以 | 正常 |
| 2–3 源 | 可以 | 顶部标一行「本稿 N 源核查，缺 xx / xx」 |
| 1 源 | 可以，但只能出**单源稿** | `meta.version` 后加「（单源稿）」，交付说明写明哪几类结论没有交叉验证 |
| 0 源 | **不许开工** | 先解决「至少能看到页面」这件事 |

## 三、接一个新连接器（30 分钟）

先想清楚：**你只需要「读」这一个能力**。写、改、发布都不需要，也不该给。

### 三条硬要求

1. **只读**。给最小权限的 token；能读代码仓就只给 read，能给知识库就只给查看。
2. **幂等**。同样的查询跑两次结果一致，不产生写操作、不触发通知。
3. **不落凭据**。token 从环境变量或交互式输入拿，不写进 `mcp.json` 之外的任何文件，不进仓库。

### 最小验收（跑通这三条才算接上）

```bash
# 用例库：能列出 3 条相关用例
# 代码仓：能读到 1 个指定文件的完整内容
# 两者：第二次调用结果与第一次一致
```

### 三种落地方式，从轻到重

| 方式 | 怎么做 | 适合 |
|:--|:--|:--|
| **A · 文件投放**（最轻） | 把导出的 `.xmind` / `.md` / 代码文件丢进工作目录，让 AI 直接读 | 一次性交付、外包项目、公司不给开接口 |
| **B · CLI** | 平台有 CLI 就包一层，像 `harvest.py be --repo` 那样 | GitHub（`gh`）、GitLab（`glab`）、自建 Git |
| **C · MCP / API 连接器** | 在 agent 的平台侧接 MCP server 或 API token，AI 通过工具调用读 | 团队长期用、需要反复跑 |

A 永远可用，任何时候都不要因为「没连上连接器」就停下来——**降级比阻塞好**。

## 四、常见组合对照

| 你的环境 | 用例源 | 代码源 | 实际能到几源 |
|:--|:--|:--|:--|
| 全云团队 | Notion / 飞书 / 语雀 | GitHub / GitLab | 6 |
| 半云 | Excel 导出 | 本地 clone | 5 |
| 只有测试环境 | 业务口述 | 无 | 3（渲染 + 接口 + 口述） |
| 外包 / 黑盒 | 无 | 无 | 2，出单源稿 |

## 五、别做的三件事

1. **不要为了让六源齐而去猜。** 缺源标出来，比凑齐一个假的六源有用一百倍。
2. **不要把「连接器没连」写成「用例库没有」。** 前者是环境问题，后者会让人以为测试没写用例。
3. **不要读生产数据、不要用生产账号。** 用例库和代码仓也分环境，拿测试分支、测试项目。
