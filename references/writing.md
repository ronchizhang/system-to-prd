# 写 PRD 的措辞与口径

> 这一份管的不是「格式」，是**写出来的话对不对**。
> 格式错了还能看出来，话写错了会一路错到实现——而且没人会回头质疑一句读起来很顺的话。

## 一、系统名 ≠ 角色名

**「管理后台」是系统，不是使用者。** 后台的使用者可能是教务、交付团队、财务、出纳、审批人。
把系统名当角色名写，句子读起来通顺，但事实是错的。

真实案例：正文写「结算申请单是**运营**真正发起付款的地方」。
实际是：自营 / 合作校 / 机构退费三类结算申请由**教务与交付团队**发起；合作校区结算申请由**系统**每天 12:00 按提现单据请求自动聚合，没有人工发起这个动作。

### 角色词表（写动作主体时从这里挑，不要自己造）

| 角色 | 干什么 |
|:--|:--|
| 教务 / 交付团队 | 发起自营、合作校、退费单据；后台新增学员 |
| 系统 | 定时聚合合作校区结算申请；按打款方式 + 币种拆合财务结算申请 |
| 财务 | 财务结算申请管理、发起财务结算申请 |
| 审批人 / 中心审批 / BP | 审批（同意 / 退回 / 流程干预） |
| 出纳 | 单据工作台、人工第三方支付操作 |
| 机构 / 合作校区 | 维护自己的收款账户与学员档案 |

### 写法

- 能确定是谁，就写具体角色：「出纳点『打款』」而不是「运营点打款」；
- 确定不了，就写**不含角色**的说法：「看单的人」「填这个字段的人」「翻这条记录的人」；
- 系统自动做的事，写「系统自动」+ 触发条件（时间、事件），不要写成某个人的动作。

## 二、先定页面定位，再写叙事

同一个页面，定位不同，场景、理由、要不要筛选——全都不一样。定位错了，后面全错。

| 定位 | 有日常读者吗 | 设计目标 | 典型页面 |
|:--|:--|:--|:--|
| **工作台** | 有，天天用 | 扫单效率、批量操作、一眼判断 | 单据工作台、审批列表 |
| **log / 记录** | **没有**，出事才翻 | 事后能还原：谁、什么时候、当时数据什么样 | 提现单据记录 |
| **审批台** | 有，待办驱动 | 判断依据齐全、动作明确、留痕 | 各类审批详情 |
| **配置页** | 有，偶尔改 | 改完即生效、影响范围清楚、可回滚 | 学员档案字段 |

**判断方法一句话：这个页面有日常读者吗？** 没有，就是 log，别给它设计筛选器和批量操作——那是给 log 装了工作台的外壳。

真实案例：提现单据记录被按「给当班人扫单看」写了两稿，实际它是「钱没到账时进来翻是谁在什么情况下提的、当时数据长什么样」。定位一改，场景要从「当班看标识做决定」改成「三周后回来查」，「要不要加筛选」的答案也从「要」变成「不要」。

## 三、量词、标点、单位不要进标签

从真实页面抄「数字 + 标签」结构时，只把**语义标签**放进标签，量词和标点归数字那侧或直接删。

| 错 | 对 | 显示效果 |
|:--|:--|:--|
| 数字 `0` + 标签 `位，打款成功学员` | 数字 `0` + 标签 `打款成功学员` | 错的那版：大字「0」一行、灰色「位，打款成功学员」一行，量词跑到行首 |
| 数字 `2` + 标签 `人，待打款` | 数字 `2` + 标签 `待打款学员` | — |

信号：**一组统计块里只有一个写对、其余都错**，基本可以确定是一次复制粘贴批量出的，要整批改。

## 四、字段是单值还是集合，看合并键

不要凭字段名判断，去看**合并/分组用的键**：

- 合并键 = `打款方式 + 打款账户`，**不含币种** → 一张单必然可能多币种 → 单头的「支付协议」必然是**集合**；
- 财务结算申请按 `打款方式 + 币种` 拆 → 它这一层是**单值**。

同一条业务，三层粒度可能不同（单头 = 集合，财务结算申请 = 单值，打款明细每人每腿 = 单值）。写 PRD 时要把这个层级关系写出来，否则实现时会拿一层的规则去套另一层。

## 五、并集宽表装不下「同名列不同义」

多协议 / 多通道的表格，如果不同行要用不同字段集合，**不要做并集宽表**，按「协议 + 币种 + 账户」分组，每组列由该协议的 schema 决定。

原因：同名列的含义可能不同——

- `通道F` 在某地区和某地区是两个不同的结算系统，同名不同物；
- `通道A` 的「银行代码」是 9 位 联行号，`通道E` 的「银行代码」是 银行代码。

一张并集表会把两个含义塞进同一列，读的人以为可以互相比对。

### 什么时候必须分组：三个触发信号

这条规则本身好懂，但**容易被绕过**——写的时候想「先画一张表，齐整」，就画成宽表了。所以记住这三个信号，
命中任一个就必须分组，不许先画表再想：

1. **表头里出现「其他 xxx 代码」**。这一列的存在本身就是并集证据：作者不知道该塞哪个字段，所以开了个收容所。
2. **同一列在不同行的值形态不一样**。比如「银行国际代码」一列，这行是 9 位数字、那行是 8 位字母，
   说明它是两种东西被强行对齐了。
3. **一行里超过 1/3 的格子是「-」或空**。这不是数据缺失，是字段集合不匹配。

反面样本（真实踩过）：合作校区结算申请详情画了一张 15 列宽表，把「国际银行账户号码 / 银行国际代码 / 其他银行代码」
并排放。三条学员分别走 通道S 与 通道E，同名列含义根本不同。业务方一眼看出：「这三条协议不一样，表头不能共用。」

### 分组之后还要写清三件事

| 写什么 | 例子 |
|:--|:--|
| **分组键** | 「协议 + 币种」；单据工作台多一个「打款账户」（因为一张打款单可能跨账户） |
| **组内列由谁决定** | 该协议的必填字段，页面不写死；新增地区只改配置，不改表结构 |
| **溢出怎么办** | 组内只列必填，点「查看结算信息」展开全部字段（含选填）；导出仍给全字段宽表 |

**分组键要按单据类型定，不能照抄。** 结算申请单已锚定一个打款账户，所以它的分组键不含账户；
打款单可能跨账户，所以含。照抄会多出一堆只有一个人的组。

## 六、口径纠偏：改一处，要扫六处

业务方说「这句话不对」时，**错的不是那一句话，是那句话背后的口径**。只改他指到的那一段，
下一次他翻到别的段落，会看到同一个错说法还在——然后第二次说同一件事。

真实案例（同一条口径被指了两次）：

| 轮次 | 我改了什么 | 漏了什么 | 后果 |
|:--|:--|:--|:--|
| 第一次 | 正文第 3 段「结算申请单是运营发起付款」→ 改成教务/系统 | `context`（为什么这样设计）、原型上的按钮说明 | 第二次被问「你 context 里还写着运营」 |
| 第二次 | 规则 statement | 第 7 段异常边界表里的「运营可代改」 | 边界表与规则互相矛盾 |

### 必须扫的六个位置

改一条口径，按这张表逐个过，**一个都不能跳**：

| # | 位置 | 为什么容易漏 |
|:--|:--|:--|
| 1 | 叙事正文（8 段里所有 `html`） | 主战场，一般会改 |
| 2 | `context`（为什么这样设计） | 它是给 AI 看的，写的时候没人回头看 |
| 3 | 第 7 段**异常与边界表** | 表格里的口径常是早期抄的，与正文两套 |
| 4 | `rules[].statement` + `cases[]` | case 里的「给定」经常还是旧口径 |
| 5 | 原型帧 HTML（按钮文案、字段名、提示语、图注） | 图上的字最容易忘，而**读的人只看图** |
| 6 | `questions[]` 与合并后的全量版 / 台账 | 待确认项若按旧口径提问，答了也没用 |

### 机械做法

```bash
python3 scripts/scan_wording.py --path modules/<key>.json \
    --term "运营发起=教务发起" --term "运营审核=审批人审批"
```

`W6` 会把**旧说法每一次出现**都列出来（正文、context、规则、原型 HTML 全在内）。
旧说法还搜得到 = 没改完。多个旧词就多给几个 `--term`。

### 两条判据

1. **口径以业务方原话为准，不要改写成自己的话再落地。** 他说「按打款方式 + 币种拆」，就写这句；
   润色成「按支付维度聚合」之后，下一个人无法判断实现是否对得上。
2. **改完把「我改了哪几处」列出来给对方。** 只回「已修正」，对方没法确认你扫没扫全——
   而这条口径他已经提过两次了。

## 七、交付前

```bash
python3 scripts/scan_wording.py --path modules/<key>.json
```

扫角色词、稿次写法、量词入标签、占位残留。红了就改，别带着跑。
`check_delivery.py` 里也挂了这一道（只报角色词 / 量词 / 占位，稿次交给「命名」组）。

## 八、一句一件事（正面例子）

规则写在 SKILL.md 硬约束 18，这里只给照抄的样本——写的时候对一眼，比读十条规则快。

### 并列拆列表：谓语提到冒号前

```markdown
**本页不支持：**
1. 批量修改状态
2. 重新提交
3. 终止
4. 按人勾选

另一个权限点也关闭。
```

注意三件事：谓语「不支持」只出现一次（在冒号前）；列表里每条只写不同部分；「另一个权限点」不属于这组，单独成句。

### 改后能数出两条就分条

```markdown
**改后：**
1. 账户块从只读 9 项扩成两段
2. 前段固定 9 项，按原顺序
3. 后段「其他结算信息」，按「字段名 → 值」一行一个往下平铺
4. 不分块、不折叠、不加「展开更多」
```

不要写成：「账户块从只读 9 项扩成两段：固定 9 项在前，下面接一小段其他结算信息，把协议要求填的字段按「字段名 → 值」一行一个往下平铺。不分块、不折叠、不加「展开更多」。」——那是 4 件事挤在一段里。

### 有编号就必须换行

```markdown
处理人实际四步：
1. 筛出待处理
2. 导出明细
3. 录入外部系统
4. 回填状态
```

挤在一行（`1. 筛出待处理；2. 导出明细；…`）等于没编号——读者看不出四步的边界在哪。

### 一段只讲一件事

```markdown
结论先说。条件跟在后面。例外单独一段。
```

一段里出现两个以上分号，说明你在同一段里讲了两件事，切开。
