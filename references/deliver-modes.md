# 两种交付：现状 PRD 与迭代 PRD

这个包能做两件事，**它们不是同一件事的深浅版本，是两个产物**。开工第一句话就要确认做哪一个。

| | **交付 A · 现状 PRD** | **交付 B · 迭代 PRD** |
|:--|:--|:--|
| 回答什么 | 系统**现在**怎么跑 | 下一版**要变成**什么样 |
| 触发句 | 「把这几个页面整理成 PRD」「给 XX 模块跑一份」「我要知道现在是怎么算的」 | 「下一版要加 XX」「基于上一稿改一版」「这次迭代改哪里，标出来」 |
| 基线 | 只有现有系统 | 上一稿全量 PRD **+** 现有系统 |
| 改动标注 | **不标**。全是现状，标了等于全标 | **必须标**。粉=已定，蓝灰=待定 |
| 稿次 | 不进入稿次序列（没有迭代线） | `第 N 稿`，全局递增 |
| 主要风险 | 漏页面、把旧注释当实现 | 上述之外，多一条：**读者分不清哪句是现状哪句是设计** |
| 谁看 | 接手的人、测试、要摸清现状的研发 | 评审、研发排期、测试写用例 |

## 一、为什么必须分开

同一句话在两个产物里含义相反：

- 现状 PRD 写「报名信息带 1 个收款币种」= **事实**
- 迭代 PRD 写同样一句 = **设计要求**

如果把现状和设计混在一份文档里、只用文字说「本次调整了币种展示」，读者要逐句判断这句是已经这样了还是要改成这样。**判断成本高到没人会去判断，最后就是照着错的做。**

所以硬规矩：

1. 现状 PRD 保持干净，一个粉块都不加；
2. 迭代 PRD 里，**没标粉的一律视为现状**（不变），标粉的才是本次改的；
3. 同一份文件里不许同时承载「现状记录」和「下版设计」。要两个都有，出**两个产物**（一份现状、一份迭代），互相链接。

> 注意别把这条和「改动版 / 全量版」搞混：那是**同一稿**的两种看法，按 2026-11-02 的约定只出一个 HTML、用标注区分；
> 而现状 PRD 与迭代 PRD 是两份不同的文档，回答的是两个问题。

## 二、共用的是底座，分叉只在两头

这两个场景**不是两套方法**。中间那一段——怎么采集、怎么核、怎么画、怎么构建——完全一样；
分叉只发生在**开工那一刻的输入**和**交付那一刻的判据**。

```
        输入（分叉）                中间（共用）                      验收（分叉）
  ┌──────────────┐        ┌───────────────────────────┐      ┌──────────────┐
A │ 一个菜单名    │  ───▶  │ 五源采集 → 事实闸门 → 骨架 │ ───▶ │ 忠实：追得到源 │
  └──────────────┘        │ → 8 段 + 原型 → 构建 → 实拍 │      └──────────────┘
  ┌──────────────┐        └───────────────────────────┘      ┌──────────────┐
B │ 菜单 + 基线稿 │  ───▶       （同一套命令、同一套模板）        │ 可指认：改了哪 │
  │ + 版本 + 范围 │                                            │ 几处、其余不动 │
  └──────────────┘                                            └──────────────┘
```

### 共用清单（做 B 的时候不要重写一套）

| 能力 | 为什么共用 |
|:--|:--|
| 只碰测试环境、凭据不落盘 | 与「记录还是设计」无关，都是碰真实系统 |
| 五源采集 + 实拍 | 迭代要改的字段、规则同样要有出处；**改之前的行为**也只能从系统和代码里读 |
| 页面清单（菜单/路由/弹窗/抽屉/页签/二级页） | 两个场景都要先知道这页有哪些入口 |
| 事实清单闸门 1 | 迭代里的新规则同样需要裁定，冲突同样不许进正文 |
| 骨架闸门 2 | 改之前先确认「这次动哪几块」，比 A 更需要 |
| 8 段结构 + 四块（原型/叙事/AI 读/核查） | 渲染引擎与契约只有一份 |
| 原型规则：`px-` 组件、禁内联样式、一页一帧、状态全集、极限值、实拍对照 | 图是给人看的，和场景无关 |
| 措辞层：角色词、页面定位、量词、集合 vs 单值、口径纠偏 | 写错话在两个场景里一样错 |
| 数据契约、构建、合并、离线单文件 | 同一套脚本 |
| 命名里的**产品版本**部分（`管理后台 V5.0`）、模块 key 规则 | 两个场景都要写清是哪个系统哪一版 |
| 验收底座：契约合规、TODO 残留、产物与数据一致、无明文凭据 | 与场景无关 |

### 真正分叉的只有三处

| 分叉点 | A · 现状 | B · 迭代 | 为什么不能共用 |
|:--|:--|:--|:--|
| **① 开工输入** | 给一个菜单名就能开工 | 必须先有四问（终端/版本/基线/范围）+ 登记 `run.json` | A 的输入是「哪里」，B 的输入是「从哪里改到哪里」 |
| **② 表达方式** | 不标 | 标粉 + 同号 + 锚点 + 台账 | A 全篇是事实，标了等于全标；B 不标则读者不知道哪句是设计 |
| **③ 验收判据** | **忠实**：每条结论追得到源 | **可指认**：改了哪几处、其余确实没动 | 两套判据查的不是同一件事，不能互相替代 |

外加一个**时间维度**的分叉：A 是「截至某日的状态」（写日期就够，不进稿次序列）；B 是「从上一稿到这一稿」（必须有稿次、基线、变更台账）。

### 顺手能省的：B 不需要重新采集的部分

迭代时最容易做过头——把整页五源重跑一遍。实际上：

- **没进入改动范围的模块**：不重采、不重画、不动数据；
- **范围内的模块里没改的段落**：沿用上一稿的正文与事实编号，只补新规则的依据；
- **必须重采的**：改动的字段/弹窗、因改动而变化的联动、以及**改动前的现状**（否则说不出「原来是什么样」）。

### 四个边界情况（共用/分叉最容易判断错的地方）

**① 迭代里整页新增的模块**

新模块没有现状可对照。这时**不要因为「不标粉」就当成现状**，也不要为了统一而给整页刷粉。
做法：**帧级角标写「本次新增」**（页面右上角一枚，不逐块刷粉），`note` 与第 1 段写明「本模块为本次新增，无现状」，
范围清单里类型写「新增整页」。读者看到「这页全新」和看到「这页没改」是两件事，必须区分。

**② 迭代里删除的东西**

删掉的功能没法在图上标——它不在图上了。**直接消失是最差的表达**：读者以为从来就没有。
做法：留一个灰块占位（`px-dislink` 或 `.px-card` 降饱和），写「本次删除：原 xxx 入口，去向：合并到 yyy」，
并在第 7 段边界表里写清存量数据怎么办。

**③ 现状 PRD 后来被当作基线**

**不许在原文件上就地加粉。** 另起一份迭代稿（新稿次、新 `run.json` 或同工作台切换 mode），原文件保持干净。
一个文件里既有「当时的现状」又有「后来的设计」，三个月后没人能还原「当时到底是怎么跑的」。

**④ 同一个工作台里既有新模块又有改模块**

`run.json` 的 `mode` 是**工作台级**的，不是模块级。整个工作台登记为 `iterate`，
新模块放进 `scope` 并标「新增整页」。不要为了一个新模块另开一个 `asis` 工作台——合并时两套稿次会打架。

## 三、交付 B 的开工四问

**这四个问题的答案不许自己填。** 问完再动手，问句可以直接照抄下面这段：

> 开工前确认四件事：
> 1. **这次改哪个终端？** 管理后台 / 主办方端 / 报名者端（三端都有的话，这次动哪几个）
> 2. **这一版的产品版本号是多少？** 比如 `管理后台 V5.0`——这是要发布的版本号，不是文档稿次
> 3. **基线是哪一份？** 上一稿的全量 PRD 是哪个文件（我按它往上加，不重画）
> 4. **本次改动范围？** 我列一版给你勾，你删改

### 为什么要问终端

三端是三个系统、三套菜单、三份数据视图。终端决定：`meta.system`、模块 `key` 前缀、菜单层级从哪一层算「三级菜单」、以及**同一个业务动作在哪一端发起**（发起端才有按钮和校验，接收端只有展示）。

搞错终端的典型后果：把「主办方端发起用款申请」画成「管理后台发起」，流程方向整个反了。

### 为什么版本号要问

产品版本是**业务决定**，不是从上一份文档推得出来的：可能跳过 V5.1 直接 V6.0，也可能这次改的是 V4.2 的补丁。

`schema.py` 的命名门禁要求 `meta.version = <系统> V<n>.<m> · <需求名> · 第 N 稿`，第一段填错，三道门禁全部拦下。

### 稿次：自己算，但要说出来

**稿次不问用户，自己识别；识别完必须念出来让用户确认。**

识别顺序（`scripts/plan_iteration.py` 已实现）：

1. 扫工作台 `run.json` 的 `draft`；
2. 扫 `modules/*.json` 的 `meta.version`，取「第 N 稿」的最大值 N；
3. 扫工作台根目录与 `out/` 里文件名带 `第N稿` 的产物，取最大值；
4. 三者取最大 → **+1 = 本次稿次**。

三条纪律：

- **同一需求名才算同一条稿次序列。** 换需求（如从「企业内训票」换成「账单拆分」）就从第 1 稿重新起，不要接着上一需求的 13 稿往下数。
- **不许从文件名猜产品版本。** 文件名里的 `V5.0` 是产品版本，后面的 `第13稿` 才是稿次，两者独立递增。
- 目录里同时存在多个需求的工作台时，先问清这次接哪一条，别把两条序列的最大值混在一起。

### 改动范围：先列，后做

**不要让人从空白想。** `plan_iteration.py` 的侦察报告会按上次产出列出全部模块（含规则数、已有的 `C{n}` 标注），
并直接生成可复制的 `--scope` 草稿——你要做的是删改，不是凭空列。

范围清单是一张表，**给用户勾选确认后才开始写**：

| 模块 | 改动类型 | 一句话 | 编号 | 是否牵动其他端 |
|:--|:--|:--|:--|:--|
| 结算工作台 | 新增 | 缺字段只提示不阻断，整单可提交 | C3 | 否 |
| 合作方用款申请 | 修改 | 协议由单值改为集合，按币种展开 | C4 | 报名者端展示需同步 |
| 财务用款申请审批 | 删除 | 删掉「业务用款申请审批」入口（已合并） | C5 | 否 |

规矩：

- **范围外的模块这一稿不动**，哪怕顺手看到 bug——记进事实清单，不擅自改。
- 范围里每一项都要有编号 `C{n}`，**全局递增**，不按模块重新从 1 起。
- 「是否牵动其他端」必须填。填「是」的，另一端要么同稿改，要么在待确认里挂一条，不能当没看见。
- 中途追加范围，**追加一行并留时间**，不要悄悄扩充。

`run.json` 里落一份机器可读的：

```json
{
  "mode": "iterate",
  "terminal": "管理后台",
  "product": "管理后台 V5.0",
  "draft": 14,
  "scope": [
    {"key": "demo-settle-workbench", "kind": "修改", "what": "缺字段只提示不阻断", "chg": ["C3"]}
  ]
}
```

`check_delivery.py` 的「迭代」组会读它：范围里的模块必须真有 `data-chg` 标注，**没标 = 说了要改但没画**。

## 四、标注的四件套

### ① 原型块级：`.px-chg`

包住一整个小模块（一张卡片、一个 block、一个统计条）。**不追元素级**——很多元素就一两个字，圈出来反而看不见。

```html
<div class="px-card px-chg">
  <span class="px-chg-bd"><i>C3</i> 缺字段只提示</span>
  ...
</div>
```

底色 `rgba(255,77,121,.09)`、虚线 `#F06292`、徽标 `#EC407A`。这三个值跟项目既有约定一致，别自己调。

### ② 表格列级：`chg-col` + `chg-flag`

只改一列时用。`th` 与同列 `td` 都要加 `chg-col`（模板的 `paintCols()` 会自动补 `td`，但手写 HTML 时要自己加）。

```html
<th class="chg-col" data-chg="C4"><span class="chg-flag">改④</span>打款方式</th>
```

列级底色必须 ≥ `.13` 并带左右虚线。实测 `.075` 在原型缩到 40% 时**等于没有**，用户会直接判定「你没标」。

### ③ 叙事：`.dchg` / `.dwip`

```html
<div class="dchg" data-chg="C4">
  <span class="dchg-bd">改④ 协议改为集合</span>
  <p>……</p>
</div>
```

`.dchg` = 已定改动（粉 `#FFF5F8` + 3px 左竖条）；`.dwip` = 方案未定（蓝灰）。**不许用粉色假装已经定了。**

### ④ 帧级改动条：`.pchg`

自动扫描当前帧的 `data-chg` 汇总成一行可点编号，**不用人工维护**。它解决的是「粉块散落，读者数不清这一帧到底改了几处」，同时是「标注有没有漏」的硬反馈：标了才出现。

### 徽标文案：新增、修改、删除要分开写

`data-chg` 只认编号（`C{n}`），**徽标文案要写清是哪一类**：

| 类型 | 徽标 | 别写成 |
|:--|:--|:--|
| 新增功能 / 新字段 | `新增 · 分段结算` | `改⑳`——读者以为原来就有，只是改了 |
| 修改既有行为 | `改⑩ 打款信息：补支付协议` | — |
| 删除 | `删⑭ 关闭「修改信息」入口` | — |

编号照旧用 `C{n}` 与 `data-chg` 配对，两者不冲突：编号是配对键，文案是给人看的。
**一整页都是新的**（比如新增报名者模块）就在帧角标写「本次新增」，不要逐块刷粉——整页粉等于没有重点。

### 编号必须两边同号

`data-chg="C4"` 在原型和叙事里指同一件事。同号才能：`both` 模式点一侧 → 两侧脉冲 + 一条粉虚线连过去；总览页按唯一编号计数（否则同一个改动在 4 段各标一次，会被读成改了 4 件事）。

### 每处标注都要带稿次：`data-draft`

**编号是跨稿累积的，稿次才是「这一次」。** 一份走到第 13 稿的需求，`C1…C23` 里可能只有 3 处是本稿改的。
只写 `data-chg` 的话，总览会报「本次改动 20 处」——读者把这句读成「这一稿改了 20 处」，
而业务方打开是想确认「这次新改的功能有没有标全」。这不是数字误差，是答错了问题。

```html
<div class="px-card px-chg" data-chg="C21" data-draft="13">
  <span class="px-chg-bd" data-chg="C21" data-draft="13">新增 · 打款方式和用款申请金额</span>
```

规矩：

1. **每个带 `data-chg` 的元素都要有 `data-draft`**，值是它**被引入的那一稿**。后来同一处又改了，就把所有标注一起改成新稿次。
2. **模块 `meta.draft` 必须等于 `meta.version` 里的「第 N 稿」**，两个数字不一致 = 同一页出现两套稿次。
3. **同一编号只能有一个稿次。** 原型标 9 稿、叙事标 13 稿，读者会以为这是两件事。`schema.py` 三种情况都拦。
4. **怎么知道该写几**：翻变更台账，看这个编号在哪一稿出现；没有台账就从 git 历史里数。
   **不要按「改到第几稿就写几」批量刷**——那等于把累积改动全说成本稿改动，比不标更误导。

渲染出来是这样：

| 位置 | 效果 |
|:--|:--|
| 总览「迭代坐标」 | 实心 pill「本稿 第 13 稿 · 改动 3 处」，后面跟一句「累计 22 处，其中本稿 3 处」 |
| 总览「本次改动」列 | 每模块两行：`2 处 本稿` / `累计 6`；本稿没动的写「本稿无 / 累计 5」 |
| 帧级改动条 | 分两段：`本稿 N` 实心粉 + `前稿 N` 灰虚线，前稿每颗胶囊后面标「9 稿」 |
| 「只看本稿」开关 | 右上角按钮，一键把非本稿的粉块/徽标/列底色收掉（`body.onlycur`），切模块不丢 |
| 侦察报告 | `plan_iteration.py` 按模块列「标注 7（本稿 1 / 前稿 6）」，本稿还没标的直接写「← 本稿还没标新的」 |

> 反过来：**现状 PRD 不写 `data-draft`**，它没有「本稿」的概念。schema 只在 `meta.version` 含「第 N 稿」时校验。

## 五、锚点跳转：`data-goto`，不是 `href="#id"`

迭代 PRD 里，「改动说明」常常在主文档、对应原型在另一栏，或者反过来。要能一键跳过去。

```html
<span class="golink" data-goto="r-demo-stl-09">R-DEMO-STL-09</span>
```

规矩：

1. **只写 `data-goto="<目标元素 id>"`，不写 `href="#id"`。**
   纯原型模式下叙事栏是 `display:none`，`href` 跳过去不会滚动，浏览器还会把 `pane-scroll` 归零，用户看到的是「点了没反应还回顶了」。
2. 点击走 `goMode("both")` → 延时 60ms（等布局切完）→ `flash(el, "start")` 定位到元素顶部。
   `flash` 第二参数默认 `"center"`，长文档里定位到段首要传 `"start"`。
3. **目标 id 必须真的存在。** `check_delivery.py` 会扫 `data-goto` 的值，在产物里找不到对应 id 就判 FAIL——跳空链接比没有链接更糟。
4. 跨模块跳转写在合并后的全量 PRD 里用 `模块key#元素id`，单模块产物里不写。

## 六、交付 B 的验收（比 A 多五条）

```bash
python scripts/plan_iteration.py --root <工作台> --check   # 终端/版本/稿次/范围 一致性
python scripts/check_delivery.py --root <工作台> --all --strict
```

多出来的六条：

- [ ] `run.json` 的 `terminal / product / draft / scope` 四项齐全
