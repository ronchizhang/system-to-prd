# 叙事怎么写（八段的每一段填什么）

> 来源：业务方给的《后台 PRD 文案写法拆解》（Axure 版 v0.3.4 逐页拆出来的）。
> 那份讲的是「一段字该怎么写」，这份讲「它该落在 8 段的哪一段」。
> v5.3 起，六段骨架（1/2/3/4/7/8）是**照抄**的，不是参考。

## 零、先分清这次在写什么

| 场景 | 写多少 | 判据 |
|:--|:--|:--|
| **迭代 PRD**（改一个已上线的系统） | **只写改动点**，以及改动点会碰到的字段与分支 | 没被这次改动碰到的东西，一句「与现状一致」带过，不复述 |
| **现状 PRD**（system → PRD，把系统拆成文档） | **全量功能**，一个按钮一个字段都要有 | 目标读者是接手的人，他手上没有系统 |

两种都遵守下面的写法，区别只在**覆盖面**。混着写是最常见的错：
迭代 PRD 把整页复述一遍，读者找不到「这次到底改了什么」；现状 PRD 只写主流程，接手的人得自己去点。

## 一、四类文字，四种职责

| 类型 | 回答什么 | 必须有什么 | 落在哪段 |
|:--|:--|:--|:--|
| **定位型** | 这是什么、谁能看、能干什么 | 位置 + 功能权限（穷举）+ 数据权限（穷举档位）+ 权限归属字段 + 数据范围 | 第 1 段 |
| **约束型** | 每个字段的边界在哪 | 控件 / 必填 / 值域或精度 / 校验时机 / 越界处理 / 默认值与来源 | 第 4 段 |
| **分支型** | 什么条件发生什么 | 矩阵表 + 「当…时」句式 + 校验链 + 计算等式 | 第 5、6 段（数据渲染） |
| **复现型** | 界面上到底显示什么字 | 原文照抄 + `{变量}` 占位 + 模板全文 | 第 4 段（标签/固定文案）、第 7 段（报错） |

四类混着写的后果：开发分不清哪句是需求、哪句是背景，于是全当参考。

## 二、六段骨架（照抄，别自己另起一套）

### 第 1 段 · 定位

五个槽，缺一个就是空壳：

| 槽 | 写什么 | 缺了会怎样 |
|:--|:--|:--|
| 数据范围 | 这个页面列出什么、一次一条还是多条 | 读者不知道自己在看全量还是切片 |
| 访问路径 | 菜单层级 + `route`；几个入口进同一页要写全 | 开发照着找错页面 |
| 功能权限 | 动作**穷举**，并明说「本页没有哪些动作」 | 照着别的页面做出多一个按钮 |
| 数据权限 | 可见范围由什么决定；没核就写「未核」 | 把「没过滤」当成「不需要过滤」 |
| 权限归属字段 | `customerId` / `projectId` 这类具体字段名 | 权限要按什么收窄说不清 |

迭代版再加两张表，这是读者最先要看的东西：

```html
<h3>二、本次改什么</h3>
<div class="tw"><table>
<tr><th style="width:24%">改动（编号）</th><th>具体</th></tr>
<tr><td><b>项目行置灰</b>（C20）</td><td>合作课程 = Demo PayLink 的行整行置灰、radio 点不动</td></tr>
</table></div>
<p><b>不改的部分</b>（容易越界）：机构选择、弹窗宽度、列数、第二步……<b>不动机构端入口，不回改已有学员</b>。</p>
```

「不改的部分」比「改了什么」更容易救场——它是给开发划边界，也是给评审一个「不用再看这些」的许可。

**反例**：「本页面用于管理提现记录，支持查询和查看明细。」——五槽全空，读完不知道谁能看、能看到谁的数据。

### 第 2 段 · 业务背景

三段，顺序不能换：

1. **现状怎么做**（今天靠什么跑、靠人的哪一步凑合）；
2. **错在哪**（不是「不够好」，是具体的失效：慢在哪、错在哪、追不回来什么）；
3. **方案与本文边界**（这次改哪一层，哪一层不碰）。

末尾一张典型场景表，四列：

```html
<div class="tw"><table>
<tr><th style="width:16%">场景</th><th style="width:26%">前提</th><th style="width:26%">页面显示</th><th>看的人据此做什么</th></tr>
<tr><td>某地区合作校区提 币种A</td><td>收款行在某地区、币种 币种A，建档判定为 通道U</td><td><code>XPay</code> <span class="px-tag blue">API</span> + <span class="px-tag purple">本地 · 通道U</span></td><td>没到账 → 先查XPay回执号，不去网银翻流水</td></tr>
</table></div>
```

最后一列是这张表的用处：**每个场景都要落到「看的人据此做什么」**。写不出这一列，说明这个场景只是数据变体，不该单独成行。

### 第 3 段 · 主流程

四列，没变的写「同前」：

| # | 步骤 | 改造前 | 改造后 | 差异 |
|:--|:--|:--|:--|:--|
| 3 | 选项目 | 该机构名下项目全部可选 | Demo PayLink 行整行置灰 | **本文的两处改动**（C20 / C31） |

- **差异列只标编号或「无」**，不写形容词。
- 流程本身不加步骤时，开头先写明「流程不变，本文不加步骤、不改顺序」——否则读者会以为漏了。
- 不属于本模块的步骤（上游/下游）在表后用一句 `note-line` 指到对应模块，不展开。

### 第 4 段 · 字段：两块，别混

**第一块 · 字段约束表**（只列这次会变的字段，其余写「与现状一致」）：

| 字段 | 控件 | 值域 / 精度 | 校验时机 / 越界处理 | 取数来源 | 本次变化 |
|:--|:--|:--|:--|:--|:--|
| 项目名称 `projectId` | 弹窗单选 | 合作课程 = Demo PayLink 的行禁用 | 点灰行不响应；「确定」仍报「请选择一条项目」 | `projectList(custId)` | 行禁用（C20） |

**第二块 · 改动点清单**，一条一个块：

```html
<h3>二、改动点（7 处，与原型上的编号一一对应）</h3>
<p>每个改动点只写四件事：<b>改前什么样 → 改后什么样 → 什么条件走哪条 → 界面上出现的文案原文</b>。</p>

<h4>（一）列表页 · 3 处</h4>
<div class="dchg" data-chg="C6" data-draft="2">
<span class="dchg-bd" data-chg="C6" data-draft="2">改⑥ 列表列：标识与协议都进这一列</span>
<div class="tw"><table>
<tr><th style="width:22%">位置</th><th style="width:32%">改前</th><th>改后</th></tr>
<tr><td>列表「打款账户」列</td><td><code>XPay</code></td><td><code>XPay</code> <span class="px-tag blue">API</span></td></tr>
</table></div>
<p><b>约束</b>：列数仍为 9 列；标签不换行、不省略。</p>
</div>
```

- **改动点全部放在第 4 段末**，按页面区域分组（列表 / 详情 / 弹窗 / 日志），一组一个 `<h4>`。
- 不要散到主流程段、异常段去——散出去以后，想统计「这稿改了几处」只能全文 grep。
- 每块只讲一件事。一块里出现两个「如果…则…」，就该拆成两条改动。

### 第 7 段 · 异常与边界

四列，「禁止做法 / 兜底」是这一段的骨头：

| 情形 | 触发条件 | 系统行为 | 禁止做法 / 兜底 |
|:--|:--|:--|:--|
| 机构名下全是 Demo PayLink | 没有任何其它课程项目 | 弹窗照开、一列全灰、确定报「请选择一条项目」 | **不加空态引导文案**（Q-02 已定） |

- 「禁止做法」写的是**别人真的会做错的那一种**，不是「请注意」。
- 两条同时不满足时先弹哪个，要写出来；写不出就是没想清楚。
- 实现细节（变量取数、接口口径）作「附录 A」挂**段末**，`data-goto` 指过去，不塞在表格中间。

### 第 8 段 · 待确认

`questions` 渲染，一行不手写。答完的把结论搬进正文，别只在第 8 段改状态。

## 三、句式模板（照抄）

```text
定位：当前菜单展示 {范围}，按 {规则} 检索。访问路径：{一级} - {二级}（{route}）
功能权限：{动作穷举}。本页没有 {不存在的动作}。
数据权限：{档位穷举}；根据 {字段} 控制 {维度}。现状：{实际观察到的情况，没核就写没核}

字段：【{字段}】：{控件}，{必填/只读}，{值域/精度}，{校验时机}，{越界处理}，取自 {模块 - 页面}

条件：当 {条件} 时，{对象}状态为"{状态}"。          ← 状态名带引号，与 UI 一字不差
双端：【管理后台】{对象}状态为"{A}"；【机构端】{对象}状态为"{B}"。
报错：若 {不满足}，则 {toast/红框/弹框} 提示："{原文}"。   ← 文案要带「为什么不行 + 怎么办」
计算：{汇总字段} = {分项1} + {分项2}；取数：{模块}（对接{方}）。
复用：逻辑参照【{模块}】-【{页面}】的 {组件}；差异点：{差异}。
待定：{方案}，待完善 / 需 {角色} 评估可行性。        ← 就地标注，不藏附录
```

## 四、两张必备的表

- **状态 × 操作矩阵**：行=状态，列=操作（列头加「操作：」前缀），格=✅/❌，末列=触发条件。
- **改动点表**（迭代 PRD 专用）：编号 / 位置 / 改前 / 改后 / 判定 / 文案原文——就是第 4 段第二块的那一串块，别再单独做一张汇总表。

二维关系一律上表。一段字里出现两个以上「如果…则…」，就该考虑上表。

## 五、禁用词（`scan_wording.py` W7 会拦）

友好提示 · 合理展示 · 视情况而定 · 根据实际情况 · 类似 · 同上 · 尽可能 · 适当 · 优化体验 · 支持多种格式 · 做好兼容 · 性能要好

改法：提示→给文案原文；分支→列全并排优先级；类似→写「参照【模块】-【页面】-【组件】+ 差异点」；
格式→列扩展名；兼容/性能→写场景与数据量，或标「需技术评估」。
**「需技术评估」是合法写法，「等」不是**（枚举要列完，或写明「由字典表配置」）。

另：`apis[].auth` 写「同上」也会被拦——把实际的鉴权方式写出来（几处接口通常共用一个 `authToken` 头）。

## 七、用例栏怎么写（v6 起必填）

**来源**：用例库里的 xmind 用例树。取回来不是直接粘贴——xmind 是「想到哪写到哪」的分支树，
读者要的是一条条能执行的用例。规整的动作有三步：

1. **按功能点归并**：同一个功能点的多个分支合成一条，输入差异写在步骤里；不要一个分支一条（几百条没人看）。
2. **砍掉不可判定的**：预期里出现「正常显示」「符合预期」的，要么补成可判定的（看到什么字、变成什么状态），要么删掉。
3. **挂规则**：每条标它守的是哪条 `R-xxx`。挂不上的（筛选、分页、导出这类页面通用行为）留空，但要能说出为什么留空。

**一条用例的粒度**：一次操作 + 一个判定点。步骤超过 6 步就拆成两条，否则失败时分不清断在哪。

```json
{"id": "TC-WDR-08", "group": "详情", "title": "多币种合并单的备注带出合并来源",
 "pre": "由 2 条提现自动合并而来的结算申请单",
 "steps": ["列表点「结算申请编号」进详情", "看学员明细表尾的备注列"],
 "expect": "备注写「由…发起的 2 条提现记录合并而来 / 于北京时间…发起提现申请」",
 "rules": ["R-DEMO-WDR-07"], "src": "用例库《提现单据记录.xmind》"}
```

**分组用页面区域**：列表 / 筛选 / 详情 / 导出 / 操作 / 异常。同一个区域排在一起，测试按区域跑，不来回跳。

**`gap` 只写「用例与现状不一致」**：用例库常是旧版，改了规则没改用例。这种不要偷偷改写用例让它通过，
写在 `gap` 里：「用例仍按 A 判，本次改为 B，需重写」。这条比用例本身有用——它标出了要重测的范围。

**挂不上规则要写原因**：筛选、分页、导出、字段渲染这类页面通用行为确实没有对应规则，`rules` 留空，但要在 `norule` 里写一句为什么（如「页面通用行为：筛选与分页」）。空着不写，门禁会当成漏挂——这不是形式，规则改了要靠它筛出重测范围。

**别做的事**：不要为凑数把同一个判定点拆成三条；不要把「页面能打开」写成用例；不要写测试数据的具体账号密码。

## 八、代码栏怎么写（v6 起必填）

代码栏只有一个目的：**让业务方判断「这个数对不对」，让研发知道「从哪下手」**。分两段，缺一不可。

### 上半段：问答（`code.plain`）

问题是**业务方真的会问的那句**，答案是**系统实际的做法**，不许出现「视情况而定」。

| 问得好 | 问得差 |
|:--|:--|
| 这个金额是谁算的？ | 金额计算逻辑是什么？ |
| 为什么同一个人两笔提现，手续费一笔有一笔没有？ | 手续费规则说明 |
| 这个「API」小标签是谁加上去的？ | 支付通道标识展示逻辑 |
| 单子卡在「待财务BP结算申请」不动，是谁没处理？ | 状态流转说明 |

答案的句式：**谁 + 什么时候 + 算出什么 + 算不出来怎么办**。

> 差：调用 `billingPaymentRequest` 接口取列表，前端按 `payMethod` 渲染标签。
> 好：标签不是存的，是打开列表时现算的——账户在XPay白名单、且这单是合作校区结算申请，两个都成立才加「API」。
> 少一个就不加，所以会出现「同一个账户，财务结算申请那栏没有标签」。

5–10 条。写不满说明这个模块的业务逻辑还没想清楚，不是「没有可写的」。

### 下半段：前端 / 后端对照（`code.fe` / `code.be`）

三列：位置 / 做什么（数据从哪来、什么条件下拒绝）/ 代码位置。
- 前端回答「界面上这个数是谁放的、什么时候取」；
- 后端回答「谁在什么时候算出这个结果、什么条件下拒绝」。
- 代码位置可以留空（写「—」），**但不能瞎填**；不确定就空着，比填错强。

### 末尾：技术遗留（`code.notes`）

并发、超时、精度、跨时区、第三方 schema 漂移——一条一句，说清「现在怎么兜、兜不住会怎样」。

**界线**：代码栏允许出现接口名、字段名、表名，因为读者是研发；但**不许把业务规则原文抄一遍**——
规则在第 1 栏，这里只讲「怎么实现」。反过来，正文里删掉的技术细节必须在这里查得到，两处都空 `check_delivery` 直接 FAIL。

## 九、实体关系与状态机（唯一保留的技术两块）

业务方也要看这两块，因为它们是业务问题：「这单卡在谁手里」「出问题往哪条单据线找」。

### `entities` 怎么写

只写**一级实体**（5–7 个），每个三行：一句话是什么 / 谁生成 / 关键点。用缩进表达从属，模板会渲染成层级卡片。

```yaml
提现记录:
  一句话: 合作校区在学员端点一次「提现」，这里就多一条记录
  谁生成: 合作校区（学员端）/ 机构代提
  关键点:
    状态从哪里来: 由关联的结算申请单状态派生，自己不维护独立状态
    归属: 合作校区所属的机构与项目，决定谁能看见
```

三条判据：
1. **「谁生成」必须写**——出问题时第一个要问的就是「这条数据谁造的」。
2. **不写字段清单**，那是代码栏的事；这里只写实体之间谁引用谁。
3. 末尾补一行 `引用方向:`，一句话说清主链和「哪一环改了不回头改后面」。

### 状态机（`transitions`）

- 状态名必须与正文、规则、原型**同一套字**（打款整单 5 档：待打款 / 打款中 / 已打款 / 部分打款失败 / 终止打款）。
- **只画已实现的迁移**。设计过但没做的（如「财务主动终止」）不要画进去，否则研发照着做。
- 每条迁移写「当…时」，不写「状态变更」。
