# 抓取与登录态复用

对应流程的阶段 1-2。目标不是"把 HTML 存下来"，而是**搞清楚这个系统有哪些状态**。

---

## 1. 前置：一个通过校验的地址

先跑守门脚本，不通过就停：

```bash
python scripts/check_test_env.py https://test1xxx.example.com/home
```

---

## 2. 向用户索取凭据（每次都要）

固定问这四项，不要一次问太多：

1. 测试环境地址（含起始页）
2. 账号
3. 密码
4. 这次先看哪个模块

**不要把答案写进任何文件。** 后续所有脚本调用都走环境变量：

```bash
export PRD_USER='...'
export PRD_PASS='...'
```

用完在 shell 里 `unset`，交付前跑 `audit_no_secrets.py` 复查。

---

## 3. 登录：优先让用户手动登，不要自己填表

**推荐做法**：让用户在受控浏览器里手动登录一次，然后复用这个已登录的会话。
理由：验证码、短信、二次验证、滑块都会让脚本填表失败，反复试还会触发风控。

```python
# 连接已开的调试端口，复用登录态
import json, urllib.request
lst = json.loads(urllib.request.urlopen("http://127.0.0.1:9222/json/list", timeout=5).read())
pages = [t for t in lst if t.get("type") == "page"]
```

用 `browser-automation-cdp` skill 的 `cdp` 模块连接，不要在脚本里重新起一个浏览器
（新实例没有登录态，等于白登）。

**必须脚本登录时**：一次填表 + 一次提交，失败就停下来问用户，不要重试超过 2 次。

---

## 4. 探骨架：先看路由，再看菜单

**不要靠点击去发现页面**，那既慢又容易漏。三个入口，优先顺序：

1. **前端路由表**：项目里的 `routes.ts` / `router.js` / 菜单配置，一次看全。
2. **侧边栏 DOM**：`document.querySelectorAll('nav a, .ant-menu-item')` 取 `href` + 文本。
3. **菜单接口**：很多后台有 `/api/menu`、`/api/user/permissions`，返回的就是权威菜单树。

记录成表：

| 模块 | 路由 | 列表总条数 | 本次覆盖 |
|:--|:--|--:|:--|
| 报名管理 | `/activity/list` | 1976 | ✅ |

**列表总条数的价值**：它告诉你这页有多少真实数据，进而决定要不要写细。
只有 24 条的页和 1976 条的页，写法规格完全不同。

---

## 5. 逐页抓取的三样东西

### 5.1 DOM 结构（拿层级，不拿全部 HTML）

只取需要的层级，取整页 HTML 会得到几百 KB 无用的 tag：

```js
// 取表格结构
[...document.querySelectorAll('thead th')].map(th => th.innerText.trim())

// 取前 3 行样本，看清列构成即可
[...document.querySelectorAll('tbody tr')].slice(0, 3)
  .map(tr => [...tr.children].map(td => td.innerText.trim()))
```

### 5.2 字段清单（表单页的重点）

```js
[...document.querySelectorAll('form .ant-form-item')].map(it => ({
  label: it.querySelector('label')?.innerText.trim(),
  required: !!it.querySelector('.ant-form-item-required'),
  control: it.querySelector('input,select,textarea')?.tagName,
  disabled: !!it.querySelector('[disabled]'),
}))
```

**必填标记、禁用态、默认值必须一起抓。** 只抓 label 等于只写了一半。

### 5.3 枚举值

下拉框的选项要展开后才在 DOM 里，或者从接口响应里拿。
优先从接口拿（`/api/dict`、枚举接口），DOM 展开容易漏项。

## 6. 分步表单：必须走完

**这是最容易偷懒也最容易出错的地方。** 第 2、3 步的页面只有提交第 1 步后才渲染，
不真走一遍根本拿不到。

真实案例：新增字段的三步向导，第 2 步是"服务类型 × 服务商 × 国家显示"的三维矩阵，
第 3 步只读回显。只截第 1 步的话，会在文档里写出"该页面用于配置字段基本信息"这种
完全错位的描述。

**走法**：
1. 第 1 步按最小必填量填，能过校验就行（不要填真实业务数据）。
2. 每步提交前截一张、提交后截一张，两相对比就能看出哪些字段是第 1 步带过来的。
3. 走完在测试库里留下一条测试数据 —— **提前问用户能不能留**，并记下主键便于清理。

---

## 7. 撞到阻断分支是好事，立刻记下来

流程走到一半被拦住（"必填项被禁用 + 红色警告"），不要绕过它，**这就是最有价值的产出**。

真实案例：某项目的工作国家字段在"项目未维护所属地区"时直接禁用，
Tooltip 提示"请维护项目所属地区/地区及服务商"。这条以前只能靠猜，
走一遍就成了可复现的事实。

记录格式：
```markdown
**阻断分支**：选择 企业内训票 项目后，工作国家字段变为禁用态
- 触发条件：项目未维护所属地区/地区及服务商
- 表现：输入框禁用 + 红色警告图标 + Tooltip 文案
- 解除方式：回到后台维护项目所属地区
```

---

## 8. 四方交叉：不确定的逻辑不要只看页面

| 来源 | 能回答什么问题 |
|:--|:--|
| 页面 DOM | 长什么样、哪些字段可见 |
| 前端代码 | 条件渲染逻辑、校验规则、默认值怎么算 |
| 后端枚举/实体 | 状态机全貌、枚举的完整取值（页面只显示部分） |
| 测试用例 | 边界条件、异常路径、业务方期望 |

典型收获：页面上的状态下拉只有 4 项，后端枚举有 9 个值 —— 说明有 5 个状态是系统内部流转的，
不该写进"用户可选项"，但要写进状态机。**只看页面会写错。**

## 9. 抓完先存原始材料

存到 `资源/<系统>-dump/` 下，一个页面一个 json：

```
资源/
├── admin-dump/
│   ├── 01-person-list.json
│   ├── 02-person-detail.json
│   └── form-field-add2.json
└── admin-shots/
    └── 01-person-list.png
```

**原始材料是你后面唯一的证据来源**，重绘和写文档时会被反复查。
json 体积很小（几十 KB），务必入库；截图可重新生成，不必入库。
