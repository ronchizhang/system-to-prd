# 已经写肥了怎么减

**先看一句判据：体量问题不能靠改措辞解决。** 有实测为证（运营后台 V5.0 第 23 稿，详见 `slim-metrics.md`）：

| 做法 | 结果 |
|:--|:--|
| 删词、删修辞、删口语 | 59,306 → 48,270 字（-19%），但平均句长 38.7 → **40.7**，用户看完还是说累 |
| 整段重写 + 砍表格列 | 59,306 → 35,439 字（-40%），句长没升，用户不再提字数 |

差别在于：**删词是在原地缩，重写是在换结构**。信息密度不变，字数就降不下去。

本文是「已经写完、用户嫌胖」时走的流程。**写作期怎么一开始就不写胖，见 SKILL.md 硬约束 20。**

---

## 零、先分流：三种「长」不是一回事

用户说「太长」，先分清楚是哪一种。分错就会用错力。

| 症状 | 真相 | 干什么 |
|:--|:--|:--|
| 某一段占了模块一半以上（字段表、改动点表） | 规格本身就有这么多 | **砍维度**：合并列、删重复维度、一句话代替一段 |
| 段落长（>110 字）、大量「因为…所以」「这是取舍不是遗漏」 | 论证混进了规格 | **删论证**，只留结论 |
| 用户说「找不到结论」「每次都要从头翻」 | 结构问题，不是字数问题 | **不要继续删**，改提摘要层 / 折叠方案 |

第三种最容易被误判成第一种。判据很简单：**如果删完字数明显降了，用户还是说累，那就是缺摘要层，停手改方案。**

## 一、量：先找到那 50%

```bash
python3 scripts/measure_doc.py 文档.html
```

输出四张表：模块 × 段的中文字数矩阵、每段占比、表格列数分布、超长段落/长句清单。

看两个数就够了：

- **哪个模块的哪一段占比最高**。第 23 稿是「字段字典与改动点」段，占模块 48–64%，全文 49%。改完它，全文降 40%。
- **表格列数分布**。改前大量 5–6 列表，改后 107 个表里 88% 是 2–3 列。

阈值（超了就必改，不用讨论）：

| 指标 | 上限 | 处理 |
|:--|--:|:--|
| 单段占模块比 | 50% | 优先重写这一段 |
| 表格列数 | 4 | 砍到 3 以内 |
| 单段落字数 | 110 | 拆成一短句 + 一张表 |
| 平均句长 / P90 | 35 / 60 | 长句清单里逐条拆 |

**不要平均用力。** 五个模块各降 8%，不如先把占一半的那段重写。

## 二、改：四条硬规则

**1. 一句一逻辑，一句话说完就停。**
一个逻辑 50–100 字讲清楚，讲不完说明它其实是两个逻辑，或者该进表。

> 旧：出纳在这个列表上做的第一个判断是「这单怎么付、付多少」。原来金额在最后、通道类型要进详情才看得到，两个判断要跑两处。本版把打款账户 + 通道标签 + 结算申请金额并进同一列，扫一眼就能决定这单是等系统自动付、还是自己要登网银。
>
> 新：账户名、通道标签、各币种金额并进一列，出纳看一眼就知道这单走自动还是人工。

**2. 一个改动点 = 标题句 + 一句结论 + 一张窄表。**（与硬约束 20.2 同一条，这是判断有没有写胖的尺子）

**3. 表格列从这四个方向砍。** 控件列 → 论证列 → 示例列 → 可合并列，详见 `slim-patterns.md` 第三节。砍完还剩宽就拆表，不要硬压。

**4. 删句子的唯一判据：不说这句，读者会不会做错。**
不会 → 删。会 → 换成一句祈使句留下。该删的七类与不能删的五类见 `slim-patterns.md` 一、二节。

---

## 三、不能动的四样

1. **八段结构、改动点编号（dchg）、交叉引用（xref）**。改的是文字，不是骨架。用户说「结构不变」的时候要当真。
2. **防错硬约束**。长得像论证，其实是规格：「回执出现未知状态不要默认成功」「失败的人绝不重发」。删了研发就会写错。
3. **状态名、字段值域、数值真值与来源**。数字可以少写解释，不能改值。
4. **规则 / 用例 / 事实的条数**。条数变了就是改业务，不是瘦身。

## 四、验：两道关，少一道都不行

```bash
python3 scripts/verify_slim.py 原稿.html 改后.html      # 结构等价
```

必须全绿：8 段不变、dchg 多重集一致、xref 集合零丢失、规则/用例/事实条数一致。**丢引用是最常见的翻车方式**——第 23 稿删掉一个人工写的 callout，连带丢了 R-PAY-COLLECT-12/19 两个引用。

```bash
# 实拍：至少截一个改动最大的模块页
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --virtual-time-budget=15000 --window-size=1500,3400 \
  --screenshot=/tmp/m.png "file:///path/to/改后.html"
```

**砍列必须实拍。** 窄栏里 5 列表会变成一字一行的竖排，结构校验查不出来。第 23 稿就踩到了：「本模块包含的页面与弹窗」表 5 个 th 写死 px（76/180/200/60），最后一列被压成竖排，改成百分比才对。

## 五、止损线

删到下面这个状态就停：

- 剩下的每一段，删掉后研发会缺一个实现依据
- 剩下的每一行表格，都是值域 / 状态 / 判定条件
- 再删就要动规则条数或状态名

这时字数已经到「只说规格」的下限。继续压就是删内容，换方案：顶部加一屏摘要（这页干什么 / 改几处 / 不动什么）+ 正文默认折叠，内容一个字不删。

三个明确的停手信号见 `slim-metrics.md` 第四节。

## 六、反模式

| 别做 | 为什么 |
|:--|:--|
| 只删词不改结构 | 字数降 19%，句长反而升，用户体感更差 |
| 一次改 5 个模块 | 先出一个最小模块做样板，让用户认语气；认错了只返工一个 |
| 把「口语化」当目标 | 把规格改成口语 = 改业务定义。要短，不要亲切 |
| 删到只剩规则还在删 | 那时删的已经是内容，止损，改提摘要层方案 |
| 用「不是 A 而是 B」句式 | 假靶子，读者没有这个误解。直接说 B（详见 `slim-patterns.md`） |
| 编造业务结论来填空 | 缩不下去就不缩，标出来问 |

## 七、工作方式：拆 → 改 → 注回

```bash
# 1. 拆：单文件 PRD → 每模块一个 JSON
python3 scripts/split_prd.py 原稿.html ./mods

# 2. 改：逐模块改 JSON（不是改 HTML）

# 3. 注回：只替换 window.PRD_DATA，前后缀不动
python3 scripts/inject_prd.py 原稿.html ./mods 输出.html

# 4. 验
python3 scripts/verify_slim.py 原稿.html 输出.html
```

**不要手改 HTML 正文。** 正文在 `window.PRD_DATA` 里，改渲染结果刷新就没；改 JSON 字符串容易少引号整页白屏。技术要求见 `slim-patterns.md` 第五节。

概览（`overview_html` / `meta`）要改的话，单独存一份从**最新改后稿**提取的 `ov_final.json`，别用 `split_prd.py --with-overview` 导出的那份——那是原稿的，会把改好的概览覆盖回去。

## 八、脚本对照

| 脚本 | 作用 |
|:--|:--|
| `scripts/measure_doc.py <html>` | 出指标报告，找最大块 |
| `scripts/split_prd.py <html> <目录>` | 拆成每模块一个 JSON |
| `scripts/inject_prd.py <源> <目录> <输出>` | 注回，只替换数据段 |
| `scripts/verify_slim.py <原> <改>` | 结构等价校验，非零退出即不合格 |
| `scripts/scan_wording.py --path <module.json>` | 逐条措辞与可读性体检（R1–R5），写作期就该跑 |
