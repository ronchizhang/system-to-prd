# 采集期交互规范

进测试环境之后怎么动，决定了两件事：**原型像不像**、**规则是不是真的**。
只点开看看，拿到的是「页面长什么样」；真提交一次，拿到的才是「它怎么拦人、怎么流转、失败时说什么」。

---

## 一、长页面：一页一帧，不许拆

**一条页面 = 一帧。** 内容超出一屏就换整页画布，不要拆成「基本信息 / 明细 / 日志」三个帧冒充三个页签。

为什么这条要写成硬规矩：

- 拆帧之后每帧只剩半屏，**看不出这页的信息密度和分块关系**——而这两件事恰好是评审时最要判断的；
- 读者会把「同一页的不同滚动位置」误读成「三个不同页面」，接着就会问「这三个页面怎么换的」；
- 拆分是单向的：一旦拆了，后面所有引用（`from: snapshot.json#p1`）都指不全。

### 怎么做

```bash
# 1. 抓的时候整页抓，不要只抓视口
python scripts/snapshot_page.py --base https://test1x.example.com \
    --url /bill/payoutWorkbench --key demo-pwb --page p1 --name 单据工作台
```

`snapshot_page.py` 抽的是 DOM 结构，不是截图，**长页不会漏**——漏只发生在「重绘成原型」这一步。

```python
# 2. 生成帧时把画布标成整页变体
frame = {"id": "P1", "name": "单据工作台", "full": True, "html": "<div class=\"px full\">…</div>"}
```

模板里 `.px.full` 会把 `min-height` 放开、把 `.px-main` 的内部滚动关掉，**画布随内容长高**，
导出截图时整页一次成图。默认的 `.px` 是 1440×≥600 的「视口」，滚动区外的内容会被裁掉。

### 例外只有一种：同页续图

内容高度超过约 3 屏（30+ 字段的超长表单）时，一帧会高到没法看。这时**仍然是一页**，只是分两段画：

| 帧 id | 图注 | `from` |
|:--|:--|:--|
| `P4` | 新增学员 · 基本信息（同页 1/2） | `snap.json#p4` |
| `P5` | 新增学员 · 结算信息（同页 2/2） | `snap.json#p4` ← **同一页号** |

两条要求：标题里写明「同页 1/2」；`from` 指向**同一个页号**，证明这是续图不是另一页。

**禁止**：为了每帧矮一点，把分块重新排列成「页签」。系统里没有这些页签，图上就不许有。

## 二、测试环境要真做，不要只看

是在测试环境，所以**能提交就提交、能改就改、能删就删、能审就审**。这不是为了「验证功能」，是因为下面这些东西**只有真操作才拿得到**：

| 只有真做才拿得到 | 只看页面拿到的是 |
|:--|:--|
| 必填校验的**原文**（「请填写收款人地址」还是「结算信息不完整」） | 一颗红星 |
| 提交后的**二次确认**文案与按钮顺序 | 猜 |
| 状态**真的**从 A 变成 B，以及变完长什么样 | 枚举里的一串英文 code |
| 失败路径：余额不足、重复提交、并发锁、权限不足 | 完全没有 |
| 审批同意/退回后，**上游**页面多了什么（重新发起？修改信息？） | 只能从后端代码倒推 |
| 列表排序、分页、筛选的真实行为（是前端筛还是后端筛） | 不敢写 |

### 操作纪律

1. **先记原值再动手。** 截图 + 记关键字段（单号、金额、状态）。改完要能说清「原来是什么」。
2. **自己造的数据自己收拾。** 新增一条 → 改它 → 删它。不要动别人的单据、不要清空列表。
3. **一次只改一个变量。** 同时改三个字段，出错了不知道是哪条规则拦的。
4. **改完立刻抓一次结构**（`snapshot_page.py` 同一页再抓一帧「改后」），别靠记忆。
5. **不可逆的、指向真实世界的动作不碰**：真实打款、真实发邮件/短信、真实结算申请、真实删除他人数据、改权限、改配置中心。这些的后果会溢出测试环境。
6. 第 5 条里**确实必须做**才能验证的（比如「退回会不会解冻资金」），**不做，标「未实做」**，在事实清单里 `cls=ask` + `proof` 写清为什么没做、依据的是哪段代码。**不要用「应该会」把它写成结论。**

### 记录格式

真操作完，在快照旁边留一条：

```json
{"page": "p3", "act": "提交新增学员（缺收款账号）", "expect": "阻断并提示",
 "got": "toast：请完善结算信息后提交", "shot": "shots/p3-act.png", "reverted": true}
```

`got` 里必须是**照抄的原文**，不是概括。原文是后面写校验规则和测试用例的直接材料。

## 三、弹窗 / 抽屉 / 子页面 / tab / 二级页：能拿到的都要拿到

这是最容易交半份活的地方。判据很硬：**`dialogs[]` 里标了 `covered:true` 的，必须各占一帧**，`check_delivery.py` 会数帧数对不对。

### 清单从四个地方凑，少一个就漏

| 来源 | 怎么找 |
|:--|:--|
| 路由表 | 前端 `umi.*.js` 里同前缀路由：`xxx/add`、`xxx/detail/:id`、`xxx/edit` |
| 页面按钮 | 「新增 / 编辑 / 查看 / 引用模板 / 导出 / 分配」逐个点，看是开新页还是弹窗 |
| 前端 chunk | 组件名带 `modal` / `dialog` / `drawer` / `popconfirm` |
| 用例库 | 用例里标了「弹窗」「xx 页面」「确认框」的节点 |

### 抓的顺序

```
主页面全貌 → 页面上的分块与表格 → 逐个弹窗/抽屉 → 弹窗里还能再开的（二级弹窗）
→ 二级页（走 URL 直连）→ 页签逐个切 → 真操作产生的新状态 → 改后再抓一次
```

四条具体做法：

1. **弹窗**：`--open "按钮文案"`。点了没反应多半是要真鼠标事件——`snapshot_page.py` 已走 `Input.dispatchMouseEvent`；仍不开就换一个入口，或从 chunk 里找组件直接推结构。
2. **页签**：`--tab "页签名"`。脚本会核对 `aria-selected`，没选中重点一次，两次不过直接报错——**因为「点了没切、但抽出来照样有内容」是最隐蔽的假数据**，曾经四帧一模一样才发现。
3. **二级页**：优先走 URL 直连（带 id 参数），比点进去稳。分步表单必须真走到第 2、3 步，第 1 步的 DOM 里没有后面步骤的字段。
4. **二次确认 / 结果页**：也各算一个弹窗。删除的确认框、提交后的结果页，文案经常是唯一写清后果的地方。

### 拿不到怎么办

写进 `dialogs[]` 并标 `covered:false`，同时在事实清单里挂一条 `cls=ask`，写清是「权限不够 / 数据造不出 / 需要审批流到某状态 / 接口 500」。

**不许**用「其他类似」四个字带过一组弹窗。读者分不清是没画还是不存在。

## 四、覆盖度自查

抓完先自己过一遍，再交给人看：

- [ ] 每个页面只有一帧（超长用「同页 1/2」续图，`from` 同页号）
- [ ] `dialogs[]` 里 `covered:true` 的每一项都有对应帧，帧里有真实内容（不是骨架「待画原型」）
- [ ] 页签逐个切过，每帧内容**不同**（抽出来一模一样就是没切成功）
- [ ] 列表页每个状态至少一行，且操作列给出该状态的动作
- [ ] 至少一个极限值样本：20+ 字姓名、4 个币种、超长账户名
- [ ] 真操作产生的状态变化有「改前 / 改后」两帧
- [ ] 没做的动作标了「未实做 + 原因」，没有一条靠「应该会」写成结论

## 五、和需求方核对

抓完把这张表发给对方，让他扫一眼就知道你缺什么：

| 页面 / 弹窗 | 类型 | 入口 | 拿到了吗 | 缺口原因 |
|:--|:--|:--|:--|:--|
| 单据工作台 | 主页面 | 财务管理 / 单据工作台 | ✅ 整页一帧 | — |
| 确认打款 | 弹窗 | 列表「确认打款」 | ✅ | — |
| 打款失败详情 | 抽屉 | 状态=打款失败 行内「查看原因」 | ❌ | 造不出失败单据 |

**读者只看得见图，看不见你没画的东西。** 缺口必须显式列出来，别指望别人自己发现。
