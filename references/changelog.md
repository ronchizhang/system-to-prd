### v5.3（2026-11-03）

**八段的位置本来是固定的，但「每段里放什么」没写死**，于是同一份 6 模块文档里八段各自为政：
定位段一句「本页面用于管理 XX」、主流程九条 `<ol>`、字段说明和改动叙述混在一段、异常十条 `<ul>` 要点。
读者读完知道有这八段，仍不知道这次到底改了什么。业务方给了一份《后台 PRD 文案写法拆解》，
要求按它重写六段——那就把它做成规则，而不是再做一次手工重写。

| 改了什么 | 位置 |
|:--|:--|
| 新增硬约束 14：**六段骨架**（1 定位五要素 / 2 背景三段 + 场景表 / 3 改前改后对照 / 4 字段两块分开 / 7 四列表 / 8 由数据渲染），并写死「迭代只写改动点、现状才写全量」的判据 | `SKILL.md` 第零节 |
| `narrative.md` 从「每段一句话描述」重写成**可直接抄的骨架**：每段给必填槽表 + HTML 片段 + 反例；发版前自检从 12 问加到 14 问 | `references/narrative.md` |
| `check_delivery` 新增「叙事骨架」组（5 条：2 FAIL + 3 WARN） | `scripts/check_delivery.py` |

**门禁能判的三条**（这次全踩过，原来一条都不报）：

1. **S1 说「共 N 处改动」，第 4 段必须有 N 个 `.dchg` 块。** 实测一个模块声明 16 处、正文只有 12 条，
   总览照写「16 处」，读者点索引过去是空的。这类「只有编号没有正文」一次扫出 5 条
   （单据工作台 C10 / C25 / C38，财务审批 C34，以及两个模块都缺的 C37）。
2. **S1 索引（`.ci` 里的 `chg-jump`）列的编号，必须都能落到正文块。** 与第 1 条互补：一个查总数，一个查具体是谁。
3. **S3 是不是有「改造前 / 改造后」、S7 是不是四列表、S1 五要素齐不齐。** 这三条判不了对错，只判「有没有按骨架写」，所以是 WARN。

验证方式照硬约束 9：**先造一份坏数据，确认门禁真的会红**——删掉一个块、把 S3 换成 `<ol>`、把 S7 换成 `<ul>`、
把 S1 的「数据权限」改掉，五条检查按预期全部触发；再拿 6 个真实模块跑，全绿无假报警。只验证「能过」不验证「能抓」，等于没做。

**顺带纠正的两处自相矛盾**（同一次扫出来的，都不是排版问题）：

- 单据工作台第 4 段的整单状态表写「出款失败」，状态机里是「终止出款」，且表里根本没有「终止出款」这一档
  → 按状态机改齐 5 档。**状态名的真值永远在 `transitions`**，散文和表格都得跟它对齐。
- 状态机里留着 `待出款 → 终止出款（财务终止）`，与「终止只有一个来源：全部失败」打架 → 删该行。
  业务方早就定过，是数据没跟上规则。

两条新的样式坑写进 `references/css-pitfalls.md` §15：`.warnbar` 是「缺段警告条」专用样式（正文用它会让
`shot_verify` 误报 sections 不足 8 段，正文强调改用 `.callout`）；`.doc code` 在 `table-layout:fixed` 的表格里
`nowrap` 会溢出到邻列被盖住半截（模板已加表格内折行兜底，**改模板时别删**）。

**为什么这次是「修订 2」不是第 16 稿**：一条新规则都没加、一个状态都没改，改的是文字的组织方式。
按判据（业务结论变没变）只能算修订。推第 16 稿会让读者以为又多了一版需求，跑去比对差异，结果白读一场。

顺带修好一处工具毛病：`merge_modules` 的坐标条原来只会按 `data-draft` 数「本稿新增 N 处」，
在「只重写叙事」的修订上会数成原稿那一批。改为读 `run.json` 的 `rev_note`：有它就换成说明文字，
pill 也从「改动 N 处」改成「不新增改动点」。**只重写表达、没动需求的修订，不该在坐标条上显示成一次需求变更。**

### v4.7（2026-11-02）

三条都是**内容层的判断**，不是格式问题，但反复踩：

1. **状态标记只在「有对照面」时才允许存在。** 「已锚定 / 待锚定」「推定 / 确认」「已同步 / 未同步」这类成对的词，
   只有在两种状态都真实会出现在数据里时才写。业务方的一句反问最能验：**「那没锚定的长什么样？」**——
   答不上来，就说明这个标记没有对照面，删掉。没有对照面的标签会让人以为还有另一条路要走，于是每条都要解释一遍。
   删标记时要连带清**整对概念**（删了「已锚定」，「推定」也站不住），否则旧的一半还在文档里。

2. **留痕类需求先定「记录口径」，再画页面。** 口径只有两种，选错了后面全要返工：
   **整对象快照**（每次操作把全部属性序列化存一份，差异读取时比对）vs **字段级埋点**（写的时候判断哪个字段变了）。
   快照落地容易、能复原当时全貌、视图可重算，代价是体积与脱敏；埋点省空间但漏埋就漏记，且新增字段要回头改每一处。
   **推荐快照**，但必须同时定四件配套：字段字典版本号、跨版本字段标「当时无此字段」、敏感字段脱敏、写入前版本校验。

3. **操作类型宁少不多。** 一张单据的操作日志通常只有两三类（创建、业务动作），
   **审批类动作不进单据日志**——审批流里本来就有节点、意见、处理人，抄一遍就是维护两份会打架的记录。
   判据：这个动作换个地方已经有记录了吗？有，就不在这里记。
   另：**操作人不一定是人**，系统回写要记「系统（SYS）」并单列触发方式（同步响应 / 异步回调），
   写成人的名字，事后分不清「这一步是人点的还是机器写的」。

### v4.5（2026-11-02）

修 4.4 带出来的两处判据过严——都是拿真实稿子跑出来的，不是推演。

1. **P0 必须写 ask**。原规则不分情况：`sev=P0` 且 `ask` 空就报错。
   但一条 `cls=fix` 且 `now` 已写清「改成什么」的事实，是**已裁定**的，它没有要问的。
   硬要求 ask，只会逼人写个「无」来糊弄门禁，门禁退化成格式检查。
   改为：`cls=fix` 且 `now` ≥10 字 → 免 ask；其余 P0 照旧。
   `schema.py` 与 `check_delivery.py` 两处判据**必须同改**——只改一处，另一处还会红。

2. **上一修订被当成「本稿产物」**。4.4 只按「稿次」圈本稿文件，于是修订 2 一出来，
   修订 1 的文件名被要求也跟着改成 `-修订2`。它明明是历史。
   改为按「稿次 + 修订号」双重判断：稿次更小的是历史稿，稿次相同但修订号更小的是上一修订，
   两者都不要求重命名。另加一条 WARN：**旧修订版别留在交付目录**，移到 `90-共享/归档/旧修订/`——
   两个名字只差一个数字的文件并排躺着，递出去必拿错。

教训：**门禁的判据要能被「已裁定」和「历史」这两类正常情况豁免**，
否则它会把合规的做法判成违规，人就会去糊弄它，最后连真违规也一起放过了。

### v4.4（2026-11-02）

**加「同稿修订」这一档。** 业务方的判断很干脆：这次的修改只动了表达与证据，没动业务结论，
所以「就是十三稿修订一，不要推十四稿」。包之前只有「第 N 稿」一个维度，
遇到这种情况只能二选一——要么推新稿（读者以为又多一版需求），要么当没改过（证据补了但版本没动，说不清）。

| 维度 | 写法 | 什么时候用 |
|:--|:--|:--|
| 产品版本 | `管理后台 V5.0` | 这次迭代发布的版本 |
| 文档稿次 | `第 13 稿` | 业务结论变了 |
| **同稿修订** | `第 13 稿（修订 1）` | **只改表达与证据，业务结论没动** |

判据只有一条：**业务结论变没变**。补快照、补台账、修措辞、补齐单边标注 → 修订；加规则、改状态流转、改字段含义 → 新稿。

落地：

| 层 | 改什么 |
|:--|:--|
| 数据 | `meta.rev` + `meta.version` 末尾的「（修订 M）」必须互相印证，缺一个或数不一样 `schema` 报错 |
| 门禁 | `merge_modules` 新增：`run.json` 说修订 1 而文件名没带 `-修订1` → **拒绝合并**；文件名带修订而 `run.json` 没有 → 也拒 |
| 开工 | `plan_iteration --set --rev N`；**推新稿时 `rev` 自动清零**（上一稿的修订号跟过来只会误导）；`--check` 查三处一致 |
| 显示 | 迭代坐标 pill 写成「本稿 第 13 稿（修订 1）· 改动 3 处」；模块索引列 `V5.0·13稿·修1`；浏览器标题带稿次与修订 |

顺手修的三处（都是实拍/跑门禁打出来的）：

1. **`plan_iteration` 扫不到产物文件名**。它只扫工作台内部，而交付物放在项目根、和 `prd-xxx/` 并排，
   于是报「文件名还没带 -修订1」的假告警。改成同时扫上一级顶层，且只收文件名带产品关键字的，避免把隔壁项目算进来。
2. **历史稿被当成错**。第 10/11/12 稿留在目录里是对的，原来一律报「文件名稿次与 run.json 不符」，
   这条告警会永远亮着，用久了就没人看。改成只报「超前」的稿次。
3. **`V5.0 · 第13稿·修1` 折成两行**（实拍量的，不是猜的）：112px 列里带空格就换行，「1」掉到第二行。
   改成 `V5.0·13稿·修1` + 列宽 118px，用 Range 量过 6 行全是 1 行。

### v4.3（2026-11-02）

**改动编号加「稿次」维度。** 拿自己的包去验一份真实迭代稿时发现的漏洞，不是猜的：

那份稿子走过 13 稿，`C1…C23` 全挂在同一份总览上，于是「本次改动」列显示 5/5/1/2/6/1 = **20 处**；
而这一稿实际只改了 **3 处**（C21 单据工作台补列、C22/C23 合作方请款）。**读者会把累积改动读成本稿改动**——
这正是业务方要求「标记这一次新改的功能」时要防的事，而包里没有任何东西阻止它发生。

| 改哪 | 怎么改 | 为什么 |
|:--|:--|:--|
| 数据 | 每个 `data-chg` 必须带 `data-draft="N"`；模块 `meta.draft` 必须等于 `version` 里的「第 N 稿」 | 编号是跨稿累积的，没有稿次就没有「这一次」的概念 |
| 门禁 | `schema.py::_check_chg_draft`：缺 `data-draft` / 稿次超过本稿 / **同一编号两个稿次**，三种都报错 | 同一编号在原型标 9 稿、叙事标 13 稿，读者会以为是两件事 |
| 总览 | 迭代坐标条加「本稿 第 N 稿 · 改动 M 处」实心 pill；「本次改动」列拆成「本稿 M 处 / 累计 K」 | 一个数字答不了两个问题：「这条需求线改了多少」和「这一稿动了什么」 |
| 原型 | 帧级改动条按本稿/前稿**自动分组**，前稿降成灰虚线并标出稿次；新增「只看本稿」开关（`body.onlycur`） | 一帧里 7 处标注只有 1 处是本稿时，人要能一键收掉其余 6 处 |

**加双重门禁。** 业务方的判断很直接：这个任务复杂，单一门禁不够用——**门禁上加门禁**。

|:--|:--|:--|:--|

让它成为「标注有没有漏」的硬反馈，而不是靠人记得。

**多协议表格的通用解法（做支付/多通道类需求会反复遇到）**

同一批数据里不同行要用不同字段集合时，不要做并集宽表，也不要硬塞进一张固定表：

1. **按「协议 + 币种 + 账户」分组**——这三项通常也正是后端拆请求的依据，分组不是为好看，是发起单位的可视化
2. **每组列 = 该协议的必填字段 + 固定尾部**（状态 / 说明 / 操作）；列清单来自接口 schema，页面不硬编码
3. **组内只列必填，行下展开看全部字段**（含选填）——展开放行下而不是弹窗，因为要跟同组其他人对照
4. 并集宽表的硬伤不是「列多」，而是**同名列在不同协议里不是同一个东西**（银行代码：清算网络A 是 routing number，清算网络E 是 银行代码），混成一列填错也不报

**原型 HTML 改块的踩坑（很隐蔽，务必照做）**

用 `rfind('<div class="px-card')` 找卡片起点会**命中 `px-card-hd` / `px-card-bd`**（前缀相同），
替换后新块被嵌进旧卡片里，页面看起来「还行」，但粉块一直罩到下一张卡片、页脚跑到粉区里。
两条纪律：

```python
# ① 只用完整标签匹配
start = h.rfind('<div class="px-card">', 0, i)
# ② 每改完一帧立刻验 div 配平
assert len(re.findall(r'<div\b', f['html'])) == len(re.findall(r'</div>', f['html']))
```

配平不为 0 就是嵌套错了，别靠肉眼。

踩过的四个坑：
1. **scroll 监听不能把线抹掉**，要重绘。`.scrollIntoView` 自己就会触发 scroll，先画线后清线等于永远画不出来。改成 `paint(id)` + `CUR` 记录当前连线，滚动时重画。

这一版全是被真实页面打出来的坑，每条都在 `scripts/` 里留了注释说明为什么：
