# 模式 ② · 迭代

> **未读本文件不许进入迭代模式。**
> 适用：已有全量基线，挑部分页面做下一版。
> 和采集模式的区别只有一句话：采集讲「原本是什么」，本模式必须讲「**为什么改**」。

---

## 本模式独占的硬约束

这两条都关于「改动怎么标、标在哪」，采集模式不需要（它不标改动）。

---

### 8 · 两种交付不许混：迭代必须可指认

做交付 B 时，四件事缺一件就不许动手：

1. **问清改哪个终端** —— 管理后台 / 企业端 / 员工端。终端决定 `meta.system`、key 前缀，以及**动作在哪一端发起**。搞错终端，流程方向整个反。
2. **问清产品版本号** —— `管理后台 V5.0`，这是要发布的版本，不是稿次。**不许猜。**
3. **稿次自己算、算完念出来** —— 扫 `run.json` / 各模块 `meta.version` / 产物文件名里的「第 N 稿」，取最大 +1。同一需求名才算同一条序列，换需求重新从第 1 稿起。
4. **先列改动范围，给对方勾** —— 模块 × 改动类型（新增/修改/删除）× 一句话 × 编号 `C{n}` × 是否牵动其他端。范围外的模块这一稿不动。

落成机器可读的四项 + 范围：

```bash
python scripts/plan_iteration.py --root <工作台> \
  --set --mode iterate --terminal 管理后台 --product "管理后台 V5.0" \
  --scope "demo-payout-workbench|修改|缺字段只提示不阻断"
python scripts/plan_iteration.py --root <工作台> --check    # 四项一致才放行
```

标注三件套 + 锚点（详细用法见 `references/deliver-modes.md` 第三、四节）：

| 改在哪 | 用什么 |
|:--|:--|
| 原型整块 | `<div class="px-card px-chg" data-chg="C3" data-draft="13">` + `<span class="px-chg-bd" data-chg="C3" data-draft="13">改③ …</span>`（**新增写「新增 · …」，删除写「删…」，别一律写「改」**） |
| 原型某一列 | `th.chg-col[data-chg][data-draft]` + `<span class="chg-flag" data-chg data-draft>改③</span>`，底色 ≥ `.13` + 左右虚线（`.075` 缩放后等于没标） |
| 叙事 | `<div class="dchg" data-chg="C3" data-draft="13"><span class="dchg-bd" data-chg data-draft>改③ …</span>`；方案未定用 `.dwip`（蓝灰） |
| 帧级汇总 | `.pchg` 自动扫当前帧的 `data-chg`，**不用人工维护**；本稿/前稿自动分组 |
| 反向定位 | 改动块右上角的「回原型 Pn」由模板按 `data-chg` 反查帧自动生成，**不用手工加按钮**；前提是原型上那处真的挂了同一个 `data-chg`（只写叙事不标图，就只剩文字没有回跳） |
| 锚点跳转 | `data-goto="<目标 id>"`，**不要写 `href="#id"`**（纯原型模式下目标 `display:none`，跳过去还会把滚动归零） |
| ~~说明条~~ | **不许**把标注挂在 `.px-gnote` 上：说明条本身要删（硬约束 11），标注要落在界面元素上 |
| 宽表（快照类） | `<table class="px-table wide">` + 外层 `.px-tw`：列多到装不下时按内容撑开、横向滚动，**不折叠不合并列**。列少的表仍用 `.px-table`（等宽铺满） |
| 快照按协议分组 | 存的是**并集**（一张宽表、写时序列化），看的时候按「协议 + 币种」拆成 N 组：`<div class="px-grp">` + `.px-grp-hd`（协议标签 / 币种 / 人数 / 该组小计 / 「全部字段」）+ 组内 `.px-table`。列宽用 `.pw1`…`.pw7` **比例类**，别和 `w-m`（px）混用——`table-layout:fixed` 下没给宽度的列只拿残值，实测被压到 40px，「1000.00」显示成「1...」。备注列加 `td.px-wrap` 允许换行，**不许截断**（出事时那格往往就是答案） |
| 弹窗里的徽标 | `.px-chg-bd` 是绝对定位，`.px-dlg` 有 `overflow:hidden`，浮到边缘会被裁一半。弹窗内改用 `.px-chg-bd.inl`（行内、无阴影） |
| 向导页 | `.px-steps` + `.px-step(.on)` 画步骤条；底部按钮用 `.px-foot.c` 居中（列表页脚是右对齐） |

**不许写内联 `style`**：`schema.validate` 会拦（「原型只允许用 px- 组件 class」）。缺什么样式就加到 `assets/module_prd.html` 里做成 class，
否则每个人画出来都不一样。

**编号 `C{n}` 全局递增，原型与叙事必须同号**；同一个改动在 4 段各标一次，会被总览读成改了 4 件事。
**粉色只用于「已定」**——方案还没定的用蓝灰，不许用粉色假装定了。

**每处标注都必须带 `data-draft="N"`（它在第几稿引入）。** 编号是跨稿累积的：一个走了十几稿的需求，
C1…C23 里可能只有 3 处是这一稿改的。不带稿次，总览的「本次改动 20 处」就会被读成「这一稿改了 20 处」——
这是业务方当场指出过的错读，现在由 `schema.py` 硬拦（缺 `data-draft`、稿次超过 `meta.draft`、同一编号两个稿次，都报错）。
模块的 `meta.draft` 必须等于 `meta.version` 里的「第 N 稿」，两个数字不一致同样打回。

### 12 · 改动标注落在哪个元素上，是有规定的

改动的视觉形式只有三种，选错会**变成界面文字**：

| 改动粒度 | 用什么 | 长什么样 |
|:--|:--|:--|
| 整块 / 整行（卡片、抽屉、kv 行） | `div.px-chg` / `div.px-kvrow.px-chg` + `span.px-chg-bd` | 粉色虚线框 + 右上角粉色徽标 |
| 整列 | `th.chg-col` + `th` 里的 `span.chg-flag` | 整列淡粉底 + 表头徽标 |
| 弹窗内 | `span.px-chg-bd.inl` | 行内徽标（`.px-dlg` 是 `overflow:hidden`，浮出去会被裁） |

**`chg-flag` 只属于表头。** 只有 `.px-table th .chg-flag` 这条规则给了徽标样式；
把它挂在 `td` / `div` 里，它就是一段普通行内文字，直接接在金额或协议名后面：

```
200.00币种A 阿联
酋改㊺                 ← 读者会以为「改㊺」是协议名的一部分
```

单格改动没有「一格专属」的标记方式，就用**整行**的 `px-chg` 把它框起来——宁可框大一点，也不要让标注混进数据。

## 迭代工序

**基线是上一稿的 `module.json`，不是新起一份。** 复制 → 改 → 重构建，编号与规则沿用，只增不改号。

### 3.1 四问 + 一次侦察

先跑侦察，把「上一次做到哪」念给对方听，再问缺的：

```bash
python scripts/plan_iteration.py --root ./prd-xpay
```

它会数出：已有终端、产品版本、稿次分布（`run.json` / 模块 / 文件名三处）、模块清单（带规则数与已有 `C{n}`）、
下一个可用的改动编号，并给出「本次应为第 N 稿」；范围没登记时**直接生成 `--scope` 草稿**，你删改即可。

然后确认四件事（话术可直接用）：

> 1. 这次改哪个终端？（管理后台 / 企业端 / 员工端，动哪几个）
> 2. 这一版的产品版本号是多少？（如 `管理后台 V5.0`）
> 3. 基线是上一稿的哪一份全量 PRD？
> 4. 改动范围我列了一版，你勾一下 —— 范围外的这一稿不动。

第 3 条不确认就动手，等于重画一份，而且**旧编号会断**（规则 `R-xxx`、改动 `C{n}` 都是引用锚点）。

### 3.2 登记

```bash
python scripts/plan_iteration.py --root ./prd-xpay \
  --set --mode iterate --terminal 管理后台 --product "管理后台 V5.0" \
  --scope "demo-payout-workbench|修改|缺字段只提示不阻断" \
  --scope "demo-partner-request|修改|协议由单值改为集合"
# 不写 --draft 就按工作台最大值 +1；写错会报「稿次倒退」
```

`--scope` 四段：`key|类型|一句话|C3,C4`。编号不写就自动分配（扫全部模块取最大 +1，**全局递增**）。

### 3.3 改数据的四条纪律

1. **只改范围内的小模块**。改动落到「一张卡片 / 一个 block / 一整列」这一层，**不追元素级**——很多元素就一两个字，圈出来反而看不见。
2. **原型先改、叙事跟上、同号**。原型标 `C3`，叙事里必须有一段 `.dchg data-chg="C3"` 解释为什么改；只标图不写为什么，读者只能猜。
3. **数字要有出处**。新增的统计、人数、金额，从后端代码或实拍里来；没有出处就标待确认，别顺手编一个看起来合理的。
4. **改一条口径要扫六处，并登记台账**。业务方说「这句话不对」时，改的是一整套口径，
   正文 / `context` / 第 7 段边界表 / `rules[].statement` 与 `cases` / 原型上的字 / 待确认项，
   **一处不改就等着被问第二遍**：

   ```bash
   python scripts/scan_wording.py --path modules/<key>.json \
       --term "运营发起=服务人员发起" --term "运营审核=审批人审批"   # W6：旧说法还搜得到吗
   ```

   改完在台账里加一条（`C{n}` / what / why / impact），四路渲染。**没登记的改动等于没发生**，
   下一稿没人知道为什么变成这样。详见 `references/writing.md` 第六节与 `references/change-ledger.md`。

> 原型画的是「改完之后的样子」，允许改实拍的值，但要在该帧 `note` 里点名哪几处不是实拍原值、底座用的是哪张真实单据。**宁可承认是设计稿，也不要让读者以为系统现在就这样。**

### 3.4 构建 + 实拍 + 迭代验收

```bash
python scripts/build_module_prd.py --data modules/<key>.json --facts facts/<key>.facts.json \
  --out out/<key>.html --strict
# 想让这一页也带左侧导航（总览 + 改动总览）：加 --nav，外壳由合并脚本生成
python scripts/shot_verify.py --html out/<key>.html          # 粉块在缩放下还看得见吗
python scripts/plan_iteration.py --root . --check             # 终端/版本/稿次/范围
python scripts/check_delivery.py --root . --all --strict      # 多一组「迭代」检查
```

`check_delivery.py` 的「迭代」组查四件（交付 A 不查）：

| 查什么 | 不过说明什么 |
|:--|:--|
| 稿次与 `run.json` 一致 | 数据还是上一稿，忘了改成第 N 稿 |
| 范围内的模块真有 `data-chg` | 说了要改，图上没标 |
| 范围编号都落到图上 + 原型与叙事同号 | 只标了图 / 只写了字，两边对不上 |
| `data-goto` 的目标 id 存在 | 锚点跳空，比没有链接更糟 |

实拍要看三件事：**粉色在 40%~60% 缩放下是否可辨**、帧级改动条是否出现、点编号能否跨栏连线/跳转。再补一件反向的：改动块右上角有没有「回原型 Pn」，点了能不能跳到那一帧并把对应粉块标亮。

## 怎么讲「为什么改」

采集侧不说为什么改——它只记录原本是什么、实际是什么，改动是零。迭代侧必须讲，而且分三层，写在不同地方：

| 层 | 写在哪 | 回答什么 |
|:--|:--|:--|
| 单条改动 | `facts[].note` | 这一处为什么这么定，不这么定会怎样 |
| 整版动因 | 第 2 段业务背景 | 这版为什么要做，不做会怎样，边界在哪 |
| 取舍 | `facts[].note` + `rules[].note` | 为什么选 A 不选 B，代价是什么 |

**`note` 写不出「不可行的方案」就是没写理由。** 只写「因为业务要求」等于没写——那是原因，不是理由。

理由一律用业务语言，不写「为了技术架构清晰」这类内部动机。读者是业务方和评审人，他们要判断的是值不值得做。

## 本模式交付前的追加检查

**交付 B 另加八条（前七条 `--check` 与「迭代」组会查，第八条人工）：**

- [ ] `run.json` 的 `mode / terminal / product / draft / scope` 五项齐全
- [ ] 稿次在 `run.json`、每个模块 `meta.version`、产物文件名三处一致
- [ ] **有修订时**：`rev` 在 `run.json`、各模块 `meta.rev`、文件名 `-修订N` 三处一致（没有修订就不填，别留空字段）
- [ ] 范围内每个模块原型里真有 `data-chg`，范围编号全部落图
- [ ] 原型与叙事**同号**（每个 `C{n}` 两边都有）
- [ ] **第 4 段有 N 个改动点块（N = 第 1 段说的「共 N 处」），索引里每个编号都点得到正文**——「叙事骨架」组会拦，自己先数一遍更快
- [ ] **每处标注都带 `data-draft`，且能筛出属于本稿的那几处**（不是只有历史改动）
- [ ] 锚点 `data-goto` 的目标 id 全部存在（没有跨处引用时不要求）；粉色在 40%~60% 缩放下仍可辨
- [ ] **总览页有「改动总览」**，一处一行：编号 / 模块 / 落在哪帧 / 改了什么 / 为什么改 / 回原型。跨模块迭代时这是唯一能通读全貌的一页；某行显示「只有标注，正文没写」，说明那处只标了图没写理由
- [ ] 本次改动已登记台账（编号连续，why / impact 都写了）
