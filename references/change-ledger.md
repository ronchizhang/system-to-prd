# 变更台账：四路同源

一次登记，四处消费。这是 PRD 能不能被信任的关键 —— 页面上的标注、文档里的说明、
变更记录页签、Markdown 台账，全部来自同一份数据，永远不可能互相矛盾。

---

## 一、为什么必须同源

如果靠人工维护四处：改了页面忘了改文档、改了文档忘了登记 CHANGELOG，
几次迭代后文档就不可信了。**不可信的 PRD 比没有 PRD 更糟**，因为有人会照着它做事。

同源的实现方式很土但有效：**一个 Python 列表 + 四个渲染函数**。

---

## 二、唯一数据源的结构

```python
CHANGES = [
    dict(
        id    = "CR-07",                       # 编号，全局唯一
        ver   = "v1.2",                        # 落入哪个版本
        date  = "2026-10-28 14:20",            # 精确到分钟
        files = ["pages.py", "docs.py"],       # 涉及文件（相对路径）
        page  = "新增/修改人员 · Step 2",        # 所属页面/视图
        loc   = "收款信息 · 银行地址下方",        # 精确到分组、字段
        kind  = "新增",                        # 新增/修改/删除/文案/待确认
        what  = "命中 清算网络A 时追加 Routing Number、Account Type 两个必填项",
        why   = "清算网络A 清算必须提供路由号与账户类型，缺一不可",
        impact= "字段数 24→26；企业端表单渲染需同步；后台字段配置需支持这两个字段",
    ),
]
```

**字段填写标准**：
- `what` 必须可核查 —— 说清"改成了什么"，不要说"优化了体验"
- `why` 必须给理由 —— 这是三个月后唯一能解释"为什么当初这么定"的东西
- `impact` 必须写下游影响 —— 字段数变化、结构变化、其他页面是否要跟着改

## 三、四路消费

| # | 消费点 | 实现 |
|:--|:--|:--|
| 1 | **页面徽标** | 改动区域套一层带 `data-chg="CR-07"` 的容器，CSS 画出粉底 + 虚线 + 右上角编号徽标 |
| 2 | **文档标注** | 文档里改动段落套 `.dchg` 类，粉底 + 3px 左竖条 + 段落开头标编号 |
| 3 | **变更记录页签** | 一个独立页面，把 `CHANGES` 渲染成可筛选的表格 |
| 4 | **Markdown 台账** | 构建时用同一份数据生成 `CHANGELOG.md`，便于 diff 和 review |

### 视觉参数（照抄，别自己调）

```css
/* 页面改动区 */
[data-chg]{background:rgba(255,77,121,.065);border:1.5px dashed #F06292;
  border-radius:8px;position:relative;}
[data-chg]::after{content:attr(data-chg);position:absolute;right:0;top:0;
  background:#EC407A;color:#fff;font-size:10px;padding:1px 6px;border-radius:0 8px 0 8px;}

/* 文档改动段 */
.dchg{background:#FFF5F8;border-left:3px solid #F06292;padding:8px 12px;}

/* 关闭标注：三处同步切类 */
.nochg [data-chg]{background:none;border:none;}
.nochg [data-chg]::after{display:none;}
.nochg .dchg{background:none;border-left:none;}
```

**关闭标注时三处都要切**：左侧页面区、右侧文档区、iframe 内部 `body`。
只切外层的话，iframe 里的徽标还在（iframe 是独立文档，不继承父级样式）。

## 四、编号规则

- **按域分段**，不共用号段。企业端用 `CR-xx`，管理后台用 `ADM-xx`。
  两个域各自从 01 递增，互不干扰。理由：不同端由不同人维护，共用号段必然撞号。
- **只增不改**：已发布的编号永久冻结。改了内容就加新编号，并在新编号的 `why` 里写"修正 CR-07"。
- **不许跳号**：交付前用 `scripts/ledger.py check` 校验连续性。
- **台账每条都要带「第几稿」**，并且与原型、叙事里的 `data-draft` 一致。
  这是本文件最容易脱节的一处：台账按稿分节写，图里却只有一个扁平编号，两边对不上时，
  总览的「本稿改动」就永远算不准。**编号是同一件事的键，稿次是它在哪一稿发生。**

---

## 五、版本策略：一份文件，两种看法

**当前约定（2026-11-02 业务方定）：全量 PRD 只出一个 HTML，不额外拆独立文档。**

原因是拆两份之后立刻出现两个真相：评审时对着改动版说「这里要改」，改完只更新了改动版，
全量版停在上一稿；下一个接手的人拿到全量版，不知道改动版里还有决定。

所以两种「看法」放进同一个文件：

| 看法 | 怎么实现 | 用途 |
|:--|:--|:--|
| **只看本次改动** | 顶栏切到「改动」视图；或总览页的「本次改动」列 + 帧级改动条 `.pchg` | 评审时聚焦变化，不用翻全篇 |
| **看完整文档** | 默认视图，粉块仍保留（可开关） | 交付用，下一个人拿到的是完整文档 |

只有一种情况才出两个文件：**交付对象明确要求分离**（例如评审包只要改动清单）。
这时全量版必须包含改动版的全部内容，且两份共用同一份台账编号——**编号不一致就是两份不同的真相。**

### 但台账必须更新

单文件不等于不用登记。每次改动仍然要在 `CHANGES` 里加一条（编号、what、why、impact），
再经四路渲染出来。**没登记 = 这次改动没有发生过**，下一稿没人知道为什么变成这样。
交付 B（迭代 PRD）的流程里，这一步和「重新构建」是同一件事，不许省。

---

## 六、规则变更不回改存量

改规则时，**存量数据按绑定当时的快照执行**，不追溯。

台账里要写清"本次改动只影响新绑定对象"，否则三个月后会有人拿着新规则去要求存量数据合规。

---

## 七、交付前自查

```bash
python scripts/ledger.py check --file <changes.py路径>
```

- [ ] 编号连续、无重号、无跳号
- [ ] 每条都有 `why`，且不是"按需求调整"这种废话
- [ ] 每条都有 `impact`，下游影响写清
- [ ] 四路都能渲染出来（页面有徽标、文档有标注、页签有记录、CHANGELOG 有条目）
- [ ] 改动已登记台账（单文件也要登记，否则下一稿没人知道为什么变成这样）
