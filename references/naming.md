# 命名规范：产品版本 vs 文档稿次

> 这条规定的来源：业务方连续两次看到 `管理后台 5.0 · V10.1` 这种写法，误以为「V10.1 是 5.0 之后的第十个子版本」。
> 实际 V10.1 只是**这份 PRD 改到了第 10 稿**。两个维度被一个 `V` 混在一起，读的人必然理解错。

## 一、两个维度，两种写法

| 维度 | 是什么 | 怎么写 | 例子 |
|:--|:--|:--|:--|
| **产品版本** | 这次迭代要发布的版本号 | `管理后台 V5.0` | 「我们做的就是 V5.0 这一版」，**不是「基于 5.0 做迭代」** |
| **文档稿次** | 这份 PRD 改到第几版 | `第 13 稿`，修订写 `第 10 稿（修订 1）` | 与产品版本无关，改多少稿都可能 |

## 二、具体落到哪

| 位置 | 正确 | 错误 |
|:--|:--|:--|
| 文件名 | `管理后台V5.0-<需求名>-第13稿.html`（修订版加 `-修订1`） | `管理后台5.0-…-V10.1.html` |
| `meta.version` | `管理后台 V5.0 · 企业内训票 支持对接云端通道C · 第 13 稿` | `管理后台 5.0 · V10.1` |
| 页内版本条 | 标题 `管理后台 V5.0`，pill `第 13 稿` | 标题 `管理后台 5.0`，pill `交付编码 V10.1` |
| 正文引用稿次 | 「第 2 稿已确认财务用款申请可合并多张用款申请单」 | 「V2.0 已确认…」 |
| 台账标题 | `## 第 13 稿（2026-11-02）· …` | `## V13.0（2026-11-02）· …` |

`Vn.m` 这个形式**只允许**表示产品版本（如 `V5.0`）。它出现在别的语义里，一律算错。

## 三、修订 vs 新稿：判据只有一条

**业务结论变没变。** 没变就是同一稿的修订，变了才推新稿。

| 只动这些 → 记**修订** | 动了这些 → 推**新稿** |
|:--|:--|
| 补证据（快照、事实台账）、补叙事解释 | 新增或推翻一条业务规则 |
| 修排版、修措辞、补口径 | 状态流转、字段含义变了 |
| 把单边标注补齐、把占位填上 | 改动范围里加了模块 |
| 把凭印象画的图换成实拍 | 业务方重新裁定了某个口径 |

### 为什么不推稿次

读者关心的是**需求有没有变**，不是**文档被改过几次**。修订写成第 14 稿，看的人会以为又多了一版需求，
跑去比对两份文档的差异，读半天发现业务上一字未改——白读一场，而且下次真的出新稿时他不会再当回事。

反过来，如果业务结论变了却只记「修订 2」，更糟：研发按旧结论排了期。

### 三处必须一致（脚本会查）

```bash
# run.json
{"draft": 13, "rev": 1}
# modules/*.json 的 meta（六个模块都要）
{"draft": 13, "rev": 1, "version": "管理后台 V5.0 · <需求名> · 第 13 稿（修订 1）"}
# 产物文件名
管理后台V5.0-<需求名>-第13稿-修订1.html
```

少一处就出事：

| 漏了哪里 | 后果 |
|:--|:--|
| 只在标题写「（修订 1）」，`rev` 空着 | 脚本读不到，下一个工具当它是初版；`schema` 直接报错 |
| 文件名不带 `-修订1` | 目录里未修订的第 13 稿和修订版并排躺着，人分不出递哪份；`merge` 拒绝合并 |
| 出了修订 2，修订 1 还留在交付目录 | 两个名字只差一个数字，递出去必拿错；移 `90-共享/归档/旧修订/` |
| `run.json` 没 `rev`，模块却有 | `plan_iteration --check` 报错 |

### 推新稿时修订号自动清零

上一稿的「修订 2」到了新稿就失去意义（它已经是新稿的基线）。`plan_iteration.py --set --draft 14` 会自动删掉 `rev`；
真要保留必须显式 `--rev`。

### 总览上怎么显示

- 迭代坐标条：`本稿 第 13 稿（修订 1） · 改动 3 处`——「修订」二字必须写出来，否则和「第 14 稿」看着一样
- 模块索引「所属迭代」列：`V5.0·13稿·修1`（一行放得下，完整串进 `title` 悬停）
- 浏览器标题：`… · 全量 PRD · 第 13 稿（修订 1）`

## 四、四道代码门禁（不是提醒）

规则写在文档里没人看，所以四处都做成了硬失败：

### ① 数据层：`scripts/schema.py::_check_naming`

- `meta.version` 必须匹配 `^管理后台 V\d+\.\d+ · .+ · 第 \d+ 稿(（修订 \d+）)?$`
- 遍历 `module.json` 的**所有字符串**，任何 `Vn.m` 只要不等于产品版本号（从 `meta.version` 取 + `V5.0`）就报错。
  正文、规则、事实、原型 HTML 全在内。
- 额外拦 `VV5.0`：批量替换时最容易把 V 加两次。

报错形态：

```
meta.version：版本写法不合规：'管理后台 V5.0 · X · V14.0'
  必须写成「管理后台 V5.0 · <需求名> · 第 N 稿」
sections[0].html：有 1 处把稿次写成了 V 版本号（V3.0）
  稿次一律写「第 N 稿」；只有产品版本能写 V5.0
```

`build_module_prd.py`、`merge_modules.py`、`check_delivery.py` 都调 `schema.validate`，所以三处都吃了这一道。

### ② 产物层：`check_delivery.py` 的「命名」组

第一道只看数据。有人直接改 HTML、或者模板文案里写死了旧版本号，数据层看不见，所以再扫一遍产物：

- 版本写法（产品版本 + 第 N 稿）
- 数据里没有 V 稿次
- 产物里没有 V 稿次
- 没有 VV 重复

### ③ 合并层：`merge_modules.py`

- `--out / --md / --json` 文件名含「管理后台」时，必须带 `第N稿`，且不许出现 `-V1.2` 这种；
  临时文件名（`full.html`）不强制，免得影响调试。
- 产物写完再自检一次：命中非产品版本的 `Vn.m` 就退出，并明确说「文件已写出，但不要拿去交付」。
- **修订号对齐**：`run.json` 有 `rev` 而文件名没带 `-修订N`，直接拒绝合并；文件名带修订而 `run.json` 没有，也拒绝。

### ④ 开工层：`plan_iteration.py --check`

- `run.json.rev`、各模块 `meta.rev`、本稿产物文件名三处一致；
- 历史稿（稿次小于当前）不要求带修订号——它们是归档，不是这一版；
- 推新稿时 `rev` 自动清零，避免上一稿的修订号跟过来。

## 五、怎么改才不出事

批量改稿次时**必须排除产品版本**，否则会把 `V5.0` 也变成「第 5 稿」——这个坑踩过：

```python
def repl(m):
    if m.group(0) == 'V5.0':        # 产品版本，原样保留
        return m.group(0)
    n, r = int(m.group(1)), int(m.group(2))
    return f'第 {n} 稿' + (f'（修订 {r}）' if r else '')
```

改完必须跑三件事，全绿才算改完：

```bash
python scripts/build_module_prd.py --data modules/<key>.json --out out/<key>.html
python scripts/check_delivery.py --root . --module <key>
python scripts/merge_modules.py --root . --out "管理后台V5.0-<需求名>-第13稿-修订1.html"
```

## 六、历史文件怎么办

旧文件不删、不原地改名，统一移到 `90-共享/归档/旧版-V命名/`。
留痕的意义是「当时确实是那么叫的」，改掉反而失真；但根目录和交付目录不能再出现不合规的名字。
