# 模式 ③ · 合并

> **未读本文件不许进入合并模式。**
> 适用：迭代做完，改动只存在于工作副本里，要装回全量基线，让下一次迭代基于新版本开始。

## 先定模型：全量是基线，迭代是补丁

本模式只有两个版本，没有第三个：

| | 是什么 | 能不能改 |
|:--|:--|:--|
| **A 全量** | 基线 | **只读。** 它是本次合并的常量，也是下次迭代的起点 |
| **B 迭代** | 工作副本，从 A 复制出来 | 只改 `scope` 里的模块 |

合并就一句话：**把 B 的 `scope` 内模块覆盖到 A 上，其余原样不动。**

所以不存在「谁改过」这个判定问题——A 就是分叉点本身。这也意味着**不需要三方合并**，只需要守住一个前提：**B 确实是从当前这版 A 复制出来的。**

### 这个前提是唯一的风险来源

一旦 B 是从**更早版本**复制出来的，合回就是拿旧内容覆盖新内容。而两道常规校验都发现不了：

- 范围校验只问「动了哪些模块」，不问「基于哪一版」
- 契约校验看结构是否合法，内容对不对它不知道

两道全绿，丢的东西不在这两道里。

**检测办法：B 里没改过的模块就是分叉点留下的指纹。** 它们与当前全量完全一致，才能证明 B 是从这版 A 长出来的。

### 两种合并别混

| | 团队协作合并 | 迭代合回（本模式） |
|:--|:--|:--|
| 输入 | N 个人各写 N 个**互不相交**的模块 | 1 个人改的**部分**模块 + 一份只读全量 |
| 动作 | 拼装（集合的并） | 替换（scope 内覆盖） |
| 工具 | `merge_modules.py --root` | 同一个脚本 + 下面两道校验 |
| 出错的后果 | 少了一个模块，看得出来 | 覆盖或越界，**看不出来** |

`merge_modules.py` 只管拼装。它不检查「说好不动的模块是不是真没动」，也不检查「B 是不是基于当前版本」——本模式的价值就是补上这两道。

## 两条路，先选一条

### A · 原地迭代（默认推荐）

直接在工作台里改 `modules/<key>.json`，改完重跑 `merge_modules.py`。

**这种情况下根本不存在「合并」这个动作**——全量本来就是从 `modules/*.json` 渲染出来的，改完的 JSON 就是新的全量。历史版本靠稿次记录保留，不靠目录副本。

风险只有一个：**没有回退点**。动手前先做一次快照：

```bash
cp -r modules modules.bak-$(date +%Y%m%d-%H%M)
```

### B · 旁支迭代

需要同时推进两条迭代线，或改动很大想留完整对照时用。

1. **复制工作台** — `cp -r prd-run prd-run-iteration`。**必须从当前全量复制**，从别处拿来的副本在下一步会被拦
2. **只改范围内的模块** — 范围在 `run.json` 的 `scope` 里，别越界
3. **验同源** — 拷回**之前**跑 `check_untouched.py --same-origin`（下面 ①）
4. **拷回，只拷范围** — 逐文件拷，不用 `cp -r modules/*`
5. **校验范围外没动** — 拷回**之后**再跑一次常规模式（下面 ③）
6. **重建全量** — `merge_modules.py --root --strict`
7. **全量验收** — `check_delivery.py --all --strict`

第 3 步为什么要在第 4 步之前：拷回去之后再验，B 和 A 已经被你搅在一起了，验不出「B 原本是不是从这版来的」。

第 4 步为什么不用通配符：`cp -r modules/*` 会把旁支里所有文件都盖回去，包括你顺手改过、但没在范围内的那几个。**越界往往不是故意的，是「看着不对顺手修一下」**——那正是需要一个机器检查来兜住的事。

---

## 校验与拷回：三道，顺序不能反

**先验来源 → 再拷 → 后验范围。** 顺序反了就白验。

### ① 合之前：B 是从这版全量复制出来的吗

```bash
python scripts/check_untouched.py --same-origin \
  --base prd-run-iteration --work prd-run \
  --scope demo-payout-workbench demo-partner-request
```

`--base` 给 B（迭代副本）、`--work` 给 A（当前全量）——**方向与常规用法是反的**，因为问的问题反了：不是「A 改了什么」，而是「B 和 A 是不是同一份」。

判定有两种，脚本自动选，不用你指定。

**有身份证，就比身份证**（新工作台都走这条）。`merge_modules.py` 每出一次全量，会在工作台根目录写一个 `origin.json`，记下这一版由哪几个模块、各自什么指纹构成。迭代副本是整目录复制的，这文件跟着走——所以它能直接回答「我是从哪一版分出来的」。

建台时 `init_run.py` 会先立一张**骨架版**（`state: skeleton`），校验时明确不采信——那会儿模块还是空的，拿它比会把「还没写」误判成「全量变了」。第一次出全量才换成正式的（`state: built`）。

```
来源身份证  prd-run-iteration/origin.json  （第 14 稿 · 2026-11-06 17:20）
当前全量 A  prd-run/modules  （12 个模块）
本次覆盖    2 个：demo-payout-workbench、demo-partner-request
────────────────────────────────────────────
  对得上  demo-home-dashboard
  变了    demo-partner-list   ← 出证之后，全量这边又改过
  全量新增 demo-approval-flow     ← 出证之后加的（合完保留即可）
```

它的好处是**不用猜**：出证之后全量动没动过，比一下就是确定答案。而且它查**全部模块**，包括你这次要改的那几个——只要 A 变过，B 就是旧版，哪怕变的地方正好要被覆盖。

**没身份证，才看胎记**（老工作台）。B 里没改过的模块是分叉点留下的指纹，两边一致才能推断同源。它的盲区是 scope 覆盖全部模块时无指纹可用，会报「未验证」。

两种判定的结论和处理一样：

| 结论 | 含义 | 怎么办 |
|:--|:--|:--|
| **对得上 / 同源** | 出证之后全量没动过 | 正常，继续 |
| **变了 / 不同源** | A 已经往前走过，B 是旧版 | **停。** 先看下面那条——可能是已经合过了 |
| **已删** | 出证时在，现在没了 | **停。** 全量删过模块，B 里还留着，合回去会复活它 |
| **全量新增** | 出证之后全量长了新模块 | 不阻塞。合完保留，不要删 |

「变了」有两种，脚本会自己分，不用你判断：

- **A 与 B 已经一模一样** → 这次改动**已经合进全量**了。B 该废弃，下次迭代从当前全量重新复制，别拿它再合一次
- **A 与 B 不一样** → 真撞车。直接合会拿旧内容盖掉全量的新内容，得重做或逐个对齐

这个区分很要紧：合完一遍之后再跑校验必然是「不通过」（因为全量已经前进了），没有这条提示，每次合完都会被自己吓一次。指纹模式没有这个区分——它看不到 scope 内，只能靠你自己回想。

「变了」出现时不要「先合进去再看着修」——那样连哪句是原样都说不清。

**它还会顺带看一眼 scope 内。** 身份证和指纹都只能证明「两份整体同源」，测不到 scope 内具体哪一段会被覆盖。所以脚本用内容包含关系再推一层：

| 看到什么 | 判断 | 意思是 |
|:--|:--|:--|
| B 包含 A 的全文 | 你在 A 上接着写的 | 正常，就是你的改动 |
| A 有 B 没有的片段 | **A 那边也改过** | 装进去会丢 |
| 两边都不包含对方 | 同一块两边都动过 | 装进去只剩 B 的版本 |

推断依据：我改的时候是在 A 的原文上接着写，所以 A 那部分必然完整出现在 B 里。反过来，A 里有而 B 里没有的内容，只可能是**收到 B 之后**才加进 A 的。

这种情况报「有条件通过」，退出码仍是 0——因为它分不清「A 后来加的」和「你自己在 B 里删掉的」。看到就确认一下，别当没看见。

**能力边界**：老工作台（没有 `origin.json`）在 `scope` 覆盖全部模块时没有指纹可用，会报「未验证」。新建的工作台出全量时自动写身份证，不受这条限制。

### ② 拷回：只拷 scope 内

```bash
for k in demo-payout-workbench demo-partner-request; do
  cp prd-run-iteration/modules/$k.json prd-run/modules/$k.json
done
```

不用 `cp -r modules/*`。通配符会把旁支里所有文件盖回去，包括顺手改过、但没在范围内的那几个。

### ③ 合之后：范围外真没动吗

```bash
python scripts/check_untouched.py \
  --base prd-run.bak-20261106 --work prd-run \
  --scope demo-payout-workbench demo-partner-request
```

退出码非 0 就是有范围外的文件被改了。**这时候不要试图「把改动合进去」**——先搞清楚它为什么被改：

| 情况 | 怎么办 |
|:--|:--|
| 是顺手修的格式/错字 | 从 base 恢复那个文件，改动挪到下一稿 |
| 是本次改动必需的连带修改 | 说明范围漏列了 → **补进 `run.json` 的 `scope` 并重新登记 `C{n}`**，不是偷偷改 |
| 是工具自动回写的 | 检查是不是 `build_module_prd.py --facts` 回写了不该回写的模块 |

第三种要特别留意：`build_module_prd.py --facts` 会**回写** `modules/<key>.json`。给某个模块单独跑构建时，它可能改到别的模块。

## 登记项：这三项同样在拷回之前查（任一不过就停）

和 ① 同源校验同一个时机，但查的东西不一样：① 查**文件来源**，这里查**登记信息**。

| 查什么 | 怎么查 | 不过说明 |
|:--|:--|:--|
| **稿次一致** | `run.json` 的 `draft` = 所有模块 `meta.draft` = 产物文件名「第 N 稿」 | 有一处没改成新稿，全量里会出现两代混排 |
| **编号接续** | `C{n}` 全局递增，本稿新增的编号 > 基线最大值 | 重号会让总览把两件事读成一件 |
| **引擎版本一致** | `merge_modules.py` 默认拒绝混版本 | 混版本会缺字段，加 `--allow-mixed` 强合等于埋雷 |

```bash
python scripts/plan_iteration.py --root prd-run --check
```

三项全绿，加上 ① 的同源通过，再往下走。

## 合并后必须重跑

```bash
# 重建全量（--strict：任一模块契约不过就终止）
python scripts/merge_modules.py --root prd-run \
  --out 全量PRD.html --md 全量PRD.md --json 全量PRD.json --strict

# 全量验收
python scripts/check_delivery.py --root prd-run --all --strict
```

`merge_modules.py` 默认拒绝未签字的模块。**签完又改了内容的，签字会自动失效**——签字时记了当期模块的内容指纹，合并前 `check_delivery` 一比就知道，不用记得手动撤销。合并前记得重签一次，或者整份 `gate.py doc` 确认一遍。

## 合并完成的判据

三条，缺一条都不算合完：

1. **全量 HTML 打开，改动条在总览页出现** — 且条数是本稿的，不是历史累计
2. **范围外的模块，正文与上一版逐字一致** — 打开旧全量对一眼，不是看 hash
3. **下一次迭代能直接基于这一版起步** — `plan_iteration.py --root --check` 报的是新稿次

第 2 条最容易被跳过。hash 校验只能证明文件没变，不能证明**渲染出来**没变——模板升级、数据同源但排序变了，都会被 hash 漏掉。
