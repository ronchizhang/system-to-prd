# 正文只说人话：技术标识下沉到附录

> 需求文档写给**做决定的人**看，不写给**写代码的人**看。
> 审批的人、验收的人、半年后回来改需求的人——他们不认 `paymentMethod`，只认界面上那个叫「打款方式」的下拉框。

这一条不是文风偏好。真实后果：正文里塞满接口名和字段名，业务方看不懂就不再逐条读，
评审会变成「你讲一段我点头」，等开发做出来才发现规则理解错了——那时候改的成本是文档里的十倍。

---

## 一、什么能写，什么不能写

| 类型 | ❌ 正文里出现 | ✅ 正文这么写 | 去哪儿 |
|:--|:--|:--|:--|
| **接口地址** | `POST /demo/activity/refund/submit` | 「出纳点『确认结算』后，系统把这批单交给银行通道」 | 附录 B |
| **返回字段** | `refundId`、`refund_amount`、`order_id` | 「这批单」「本单总金额」 | 附录 B |
| **业务字段名** | `paymentMethod`、`refund_channel` | 界面上那一列的字：「打款方式」「支付协议」 | 附录 B |
| **常量 / 枚举名** | `Constant.TICKET_GROUP`、`TICKET_SWITCH_LOCK_FORMAT` | 「企业内训票 项目」「同一个人在同一次结算里的锁」 | 附录 B |
| **表名 / 状态码** | `payment_pending`、`in_progress`、`transitions` | 「待结算」「结算中」 | 附录 B |
| **实现手段** | 落库、幂等、序列化、schema、轮询、回调 | 说**它保证了什么**：见下表 | 附录 B |
| **页面路径** | `管理后台 → 财务管理 → 结算工作台` | 照写，**这个要留** | 正文 |

**页面路径要留**：那是「人怎么走到这个页面」，是业务语言。要下沉的是**接口地址**，不是页面路径。
两者长得很像（都是 `/xxx/yyy`），区别是：能在浏览器地址栏里敲出来的是页面，要靠程序调的是接口。

**代码块（`<code>`）只允许出现在附录 B**。正文里出现 `<code>` 基本就说明在讲实现。

## 二、把实现词换成「它保证了什么」

技术词之所以会溜进正文，是因为它在原作者脑子里就是「这个东西的作用」。翻的时候别删，换成结果。

| 技术词 | 换成 |
|:--|:--|
| 落库 / 入库 | 存下来、记为、系统留下这条记录 |
| 幂等 | 重复点也只生效一次 |
| 序列化快照 | 把当时那张单原样复印一份存起来，之后改档案不影响这份复印件 |
| 接口返回 / 回执 | 银行（通道）回话；回话了才算数 |
| 轮询 / 定时拉取 | 系统每隔 X 分钟去问一次 |
| 回调 / webhook | 对方主动把结果推回来 |
| schema / 数据结构 | 数据格式的规定；对方改了格式我们这边就会对不上 |
| 枚举 / 字典值 | 固定选项；选项清单 |
| 校验 / 前置校验 | 提交前先检查 |
| 缓存 | 先取一份放旁边，不用每次重新算 |
| 并发 | 两个人同时操作 |
| 事务 | 一起成功或一起失败，不会只做一半 |
| 灰度 / 开关 | 先对一部分人开 |
| 超时 | 等到规定时间还没回话 |

**判据一句话**：这句话删掉之后，业务方还需要知道什么才能做决定？如果需要，那它就该用业务语言留在正文。

## 三、复杂逻辑给 case（不是举例，是把规则跑一遍）

规则写得再准，也会有人理解偏。**一条规则配一个 case，比加三句限定管用。**

### 什么时候必须给

满足任一条就配 case：

- 规则里有 **≥2 个条件同时成立**（「协议是 跨行通道 **且** 币种是 EUR」）
- 有**例外分支**（「一般这样，但金额超过 50,000 就不这样」）
- 涉及**多人 / 多单 / 多币种**的合并与拆分
- **两条规则会打架**，需要说清谁先
- 状态**会回退或跳档**（失败后又回到待处理）

### 怎么写（五要素，不超过 5 行）

```
例 2｜香港报名者退款，走本地清算
张三是香港场次的合作方，收款账户是当地银行卡、币种 HKD。
他退款 1,000 HKD，系统按「本地 · FPS」这条协议结算。
银行回话成功 → 单据变「已结算」；本月这是第二笔，另扣 20 HKD 手续费。
```

拆开就是：**谁**（有身份、有前提）→ **做什么**（具体动作、具体金额）→ **系统怎么反应**（判定 + 结果）→ **看的人据此做什么**（可选）。

### 三条禁忌

1. **别用「例如某客户」**。写成「张三」「香港场次」——具体的名字才让人代入。
2. **别只写 happy path**。真正需要 case 的是拐弯的地方；只写顺利那条等于没写。
3. **别把 case 写成测试用例**（点哪个按钮、断言什么）。case 是给**读需求的人**做判断用的。

### 放哪儿

- 规则级 case：跟着规则走，写在该规则下面，标「例 N」
- 模块级典型场景：第 2 段末尾的典型场景表（场景 / 前提 / 页面显示 / 看的人据此做什么）
- 别单独开一节「举例说明」——脱离上下文的例子没人回去对照

## 四、附录 B：技术与字段对照（正文的下沉目的地）

每个模块第 7 段末尾挂一张表。**只写正文里出现过、研发真的需要反查的那些**，不要把所有字段抄一遍。

```html
<h3 id="apx-tech">附录 B · 技术与字段对照</h3>
<p>正文用的是界面上看得见的说法。这张表是给研发反查用的，业务方看不看都不影响理解。</p>
<table class="tech-map">
  <thead><tr><th style="width:24%">正文里的说法</th><th style="width:20%">界面位置</th><th>实际对应</th></tr></thead>
  <tbody>
    <tr><td>打款方式</td><td>列表第 3 列</td><td><code>paymentMethod</code></td></tr>
    <tr><td>支付协议</td><td>明细「打款信息」块</td><td><code>paymentScheme</code> + <code>refund_channel</code></td></tr>
    <tr><td>「确认结算」</td><td>抽屉底部主按钮</td><td><code>POST /demo/activity/refund/submit</code></td></tr>
  </tbody>
</table>
```

规矩：

- **表格用 `class="tech-map"`**：检查脚本只豁免这张表里的技术标识，别的地方出现照样报错。
- **左侧必须先写正文里的说法**，不能直接列字段名——否则研发能查、业务方还是看不懂。
- 接口只写**一个动作对应一个接口**，不要贴参数列表（那是接口文档，不是 PRD）。
- 不确定的留空，别猜。

## 五、写完自检 8 问

1. 把这份文档给一个**没参与需求**的业务同事看，他能说出「这版到底改了什么」吗？
2. 正文里还有 `<code>` 吗？（除了附录 B）
3. 有没有哪句话，只有懂代码的人才看得懂？
4. 每一条**带条件**的规则，是不是都有一个 case 跟着？
5. case 里有没有具体的人、具体的金额、具体的币种？（不是「某客户」「一定金额」）
6. 例外分支在 case 里出现了吗？还是只写了顺利那条？
7. 附录 B 的左侧，写的是**界面上的字**还是字段名？
8. 技术细节删掉之后，研发还能干活吗？（不能 → 说明附录 B 漏了，补进附录，别塞回正文）
