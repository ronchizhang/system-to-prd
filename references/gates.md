# 双层门禁

> 一层门禁的问题是：**它既当运动员又当裁判**。脚本查完数据说「合规」，但它查的是自己刚才写的数据；
> 人说「确认过了」，但没有第二个人能证明他确认的是哪一版。
> 所以门禁要叠：**第一层证明「做过」，第二层证明「做对了」，两层用不同的角度，且不允许同一个人包办。**

---

## 一、两层各管什么

| | 层 1 · 过程门 | 层 2 · 交付门 |
|:--|:--|:--|
| 谁在把关 | **人**（产品经理本人） | **机器**（反查） |
| 证明什么 | 该确认的**确认过**：事实裁定、骨架认可、封板 | 确认的东西**真的在产物里** |
| 什么时候 | 每个阶段出口，过不了不能进下一步 | 交付前 / 合并前 |
| 留痕在哪 | `facts/<key>.facts.json` → `gate` | 同文件的 `signoff` + `check_delivery` 输出 |
| 能伪造吗 | 能（自己填个时间），所以要求署名，且封板记内容指纹 | 机器项伪造不了 |

**关键：层 2 不复用层 1 的结论。** 层 1 说「事实清单答完了」，层 2 不会因此认为正文没问题——
它自己从产物 HTML 反着查一遍。两层查同一件事才叫冗余；查不同角度才叫门禁。

---

## 二、层 1 · 过程门（两个关口）

| 关口 | 问什么 | 命令 |
|:--|:--|:--|
| **闸门 1 · 事实** | 五源核查的清单，对方**逐条裁定**了吗？冲突有没有悬着？ | `gate.py facts --by <姓名> --total N --answered N` |
| **闸门 2 · 骨架** | 8 段写什么、规则大概几条、状态机几个态、**哪些不写**，认可了吗？ | `gate.py scope --by <姓名> --what "8 段 / 22 条规则 / 7 态 / 不写供应商单据"` |

规矩：

1. **`--total` 与 `--answered` 不等就拒绝**——还有没答的，不叫「已裁定」。
2. `--by` 必须是真名。系统里没有「admin 确认过了」这种留痕。
3. 骨架门不许只写「已确认」。要写清确认了哪几个数字，否则三个月后无法判断改没改范围。
4. 老的 `gate.approved_at`（只有时间没有署名）仍然认，但 `status` 会提示补署名。

---

## 三、层 2 · 交付门（机器反查 + 双人签字）

### 2a 正向：数据 → 产物（原有）

契约合规、TODO 残留、产物与数据逐字节一致、无明文凭据、命名、措辞。
这一层回答「我写的数据本身对不对」。

### 2b 反向：产物 → 数据（`[反查]` 组）

方向反过来：**假设产物是别人给我的，我能不能在数据里找到依据。**

| 查什么 | 抓的是哪种错 |
|:--|:--|
| 每条规则 id 都在产物里出现 | 数据写了、模板漏渲染 → 读者看到的是一份缺规则的 PRD |
| 每条 P0 事实都被至少一条规则或段落引用 | 核了一堆事实但正文没用上 → 读者不知道它影响了什么 |
| 已答问题的答案 ≥6 字 | `answer: "已确认"` 这种空话 |
| `covered:true` 的弹窗名出现在帧名或帧说明里 | 清单里说画了，图上找不到 |

这四条只有反着查才查得出来：正向检查看到的是「数据完整」，反向检查看到的是「读的人到底有没有」。

### 2c 人：封板（`[签字]` 组）

**一个人签，签的就是产品经理本人。** 它的性质是**封板**，不是双重确认——意思是「这一版我认了，可以往研发走」。

| 规矩 | 为什么 |
|:--|:--|
| **一个人封一次就够** | 不搞业务 + 技术两个角色互相确认，那套在真实团队里没人执行，结果是每轮检查挂红叉，红叉挂久了就不传递信息 |
| **封的是内容，不是名字** | 封板时记下当期模块的指纹；之后谁改了内容，这封**自动失效**，不用记得手动 `revoke` |
| **可以用整份代替逐个** | `gate.py doc` 一次盖住全部模块；模块多的时候不必逐个封 |

第二条是要点。只记「谁封了」不够——封完再改内容，名字还在，那就成了盖章。所以 `sign` 和 `doc` 都会记一份语义指纹（忽略缩进与键序，只认内容），`check_delivery` 每次比对：

```
! 已封板   张三 封的是旧内容——这个模块在封板之后被改过。
            重新封一次：gate.py sign --by <姓名>
```

`gate.py revoke` 仍然保留——主动撤封比等它失效更明确，尤其是「我知道要改，先撤了再改」这种。

命令：

```bash
# 逐个封（改哪个封哪个，最精确）
python scripts/gate.py sign --root . --module <key> --by 张三 --note "这一版可以往下走"

# 整份封（一次盖住全部模块）
python scripts/gate.py doc  --root . --by 张三 --note "整份看过，可以发"
```

### 严格模式才是真门禁

`check_delivery.py` **不带 `--strict`** 时，反查与签字的问题只报提醒（日常改稿不该被签字卡住）；
**带 `--strict`** 才按未通过算。交付与合并一律用 `--strict`。

## 四、层 3 · 合并门（跨模块）

单模块全绿 ≠ 全量 PRD 可用。合并这一环再查两件：

1. **封板齐**：`merge_modules.py` 默认要求每个模块都封过板；缺就拒绝，`--allow-unsigned` 只能出内部评审稿。
2. **合并后复核**：规则编号跨模块撞号、命名、产物自检；结果写进 `merge_report.json`（含每个模块谁签的、谁没签、有没有撞号）。

```bash
python scripts/check_delivery.py --root ./prd-run --all --strict
python scripts/merge_modules.py --root ./prd-run --out 管理后台V5.0-XX-第3稿.html --strict
cat ./merge_report.json
```

## 五、常见绕过，以及被谁拦住

| 想省事的做法 | 谁拦 |
|:--|:--|
| 自己填 `approved_at` 就算过闸门 1 | 层 2 要求署名；`gate.py` 记 `by`，`status` 会显示「未署名」 |
| 事实清单还有 3 条没答，先封板 | `gate.py facts --total 12 --answered 9` 直接拒 |
| **签完字再偷偷改内容，不推新稿** | 签字时记了内容指纹，改了就失效——这一条以前是漏的，只看稿次时改内容不推稿永远查不出来 |
| 改完格式（缩进/键序）不算改内容 | 指纹是语义的，格式变化不误伤，不逼人重签 |
| 数据里改完忘了重建 | 正向「页内数据 = json」 |
| 重建了但模板漏渲染 | 反向「规则都在产物里」 |
| 图是照记忆画的 | 「原型有实拍快照吗」+ `from` 指向的快照页号 |
| 只交单模块，不合全量 | 合并门要求每个模块都封过板 |

## 六、别再加第四层

三层的分工已经清楚：**过程（人确认）→ 交付（机器反查）→ 合并（跨模块）**。
再叠就变成填表：每加一层，人多绕一步，最后所有人都在机械地跑命令，没人真看内容。

判断要不要加一层，只问一句：**它能不能抓到前一层抓不到的错？** 不能，就别加。
